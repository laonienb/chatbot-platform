# 跨 harness 协同总线（harness bridge）

两套 Qoder 团队在**同一个项目、同一台机器、同一个 git 工作树**上协作：

- `G` = Qoder（国际版，用户目录 `~/.qoder`）
- `C` = Qoder CN（用户目录 `~/.qoder-cn`）

两边各自有 **架构师 / 开发工程师 / 工作区管家**。管家只负责协同，不负责业务判断。

## 一、为什么走文件总线（实测约束，别重复探索）

| 探测 | 结果 |
|---|---|
| `list_chat_sessions`（G 侧调用） | 只返回 G 的会话，**看不到 `工作区管家-C`**——会话 API 按产品隔离 |
| `qoderclicn` / `qodercn.exe` | 不在 PATH；`~/.qoder-cn/bin` 仅有 computer-use；两边 `~/.qoder*/ipc/` 为空目录 |
| 结论 | **不存在跨 harness 的会话注入或进程唤醒**。唯一共享媒介是文件系统 |
| `skill_manage` 跨根同名 | 本侧 `create` 返回 `SKILL_TARGET_MISMATCH`（同根则为 `SKILL_ALREADY_EXISTS`）。但**磁盘上两根可同名并存**：`frozen-snapshot-peer-review` 现同时存在 `~/.qoder-cn/skills/`(22:07) 与 `~/.qoder/skills/`(22:20，手拷落盘且被正常发现) ⇒ 精确说法是「**创建守门跨根去重**」，不是「Skill 名全局唯一」；同步只能文件拷贝。⚠️ 守门机制的内部原理仍是 **G 单方登记，C 侧未复核**，引用时不得写成"两边都验过" |

## 二、目录布局与铁律：每个文件只有一个写者

```
harness/bridge/
├── PROTOCOL.md        # 本文件，两边共同遵守的唯一总线条文（必须保持已提交，见 §六 🔴）
├── .gitignore         # 传输文件不入库
├── inbox/G.md         # 给 G 的消息 —— 只有 C 写
├── inbox/C.md         # 给 C 的消息 —— 只有 G 写
├── cursor/G.txt       # G 已处理到哪个 id —— 只有 G 写
├── cursor/C.txt       # C 已处理到哪个 id —— 只有 C 写
├── heartbeat/G.json   # G 的存活证据 —— 只有 G 写
├── heartbeat/C.json   # C 的存活证据 —— 只有 C 写
└── leases/G/*.lock    # G 的认领 —— 只有 G 写（leases/C/ 同理）
```

**单写者是不需要锁的前提**：谁都不写别人名下的文件，因此不会交错、不会互相覆盖。要传递信息就追加到**对方**的 inbox，绝不改自己的 inbox。

总线目录里的瞬态信号不入库，所以**删掉它不会丢历史**；反过来，`PROTOCOL.md` 与 `.gitignore` **必须入库**——协议一旦不被提交，§七 的审计机制就是空的（见 §六 🔴）。

## 三、消息格式

一条消息 = `---MSG` 开头的一行 + 其正文，直到下一个 `---MSG` 或文件末尾：

```
---MSG id=1791643200000-G ts=2026-10-10T22:40:00+08:00 from=G to=C type=task ref=AGENTS.md#〇.3 reply=none---
诉求正文（可多行）。要写清：要对方做什么、为什么、期望回什么、是否阻塞。
```

- `id` = `<epoch 毫秒>-<写者>`，全局唯一且可排序；接收方按毫秒部分排序。
- ⏱ **`ts` 只是写者自报的可读标注，不是事实**：**偏差方向不定，实测可达百余秒**。四样本：偏早 53 秒、偏早 20 秒、偏晚 27 秒、偏晚 111 秒。本条原写「实测系统性偏早」，由 C 于 `1791713071233-C` 点名纠正、G 侧同数确认（G 自己的 `1791712620000-G` 头写 `ts=17:57:00`，而 `inbox/C.md` 落盘 mtime = 17:56:33 ⇒ 偏晚 27 秒），C 的会签覆盖改后的措辞。⇒ **跨侧排序与时序认定一律以文件 mtime 为准**，需要精确时刻时 `stat` 文件，既不信 `ts` 也不信消息头。
- 🧾 **`id` 与 `ts` 必须在「执行写入的那一条命令」里现取，不得事后手写或取整**（本句是 G 对 §三 原规则的**加强**，非 C 所提；**C 已于 `1791714105560-C` 第 1 点按 commit `09b266e` 文本会签认**，并确认归属标注无误）。两侧都有过犯，各自留凭据：
  - **G 侧过犯**：`1791643760000-G`／`1791710637000-G`／`1791710949000-G`／`1791711805000-G`／`1791712620000-G` 尾数全为 `000`，即整秒手写值；G 自 `1791712398880-G` 起改为现取。
  - **C 侧过犯与修正**：`1791711850000`／`1791712230000`／`1791712500000` 同为整秒手写（C 自报于 `1791713071233-C`），其 18:04 批次改为现取后 G 侧可核：`1791713114640-C` 的 id 与 `inbox/G.md` mtime `18:05:14.677` 仅差 **37 毫秒**；G 本轮再核一条：`1791714178122-C` 的 id 与 `inbox/G.md` mtime `18:22:58.158` 差 **36 毫秒**，两个独立样本同数。
  后果与边界：按 id 排序对**过犯批次不可靠**，凡此前依据那批 id 的相对顺序做过时序推断，一律降级为「未证」。**但旧批次无法事后重算**——追加式单文件只保留最后一次 mtime，逐条落盘时刻没有留存；所以本条只能向前生效，这也正是「现取」必须是纪律而不是补救的原因。
- `type` ∈ `task`（派活）/ `reply`（答复）/ `ack`（收到）/ `decision`（结论）/ `warn`（告警，含租约冲突）。
- `ref` = 关联的文件、条目或 commit；`reply` = 被回复消息的 `id`。
- 🎯 **`reply`/`ref` 里的 id 必须从本轮锚定列举的实际输出里取值**（C 提于 `1791716591115-C`、G 成文 ⇒ **本轮新增，待 C 会签**）：不得凭记忆，**更不得拿临时 `date` 出来的 epoch 换算成一个 id**。追加发送后回读一次锚定列表，确认被指向的 id 真存在于对方 inbox。
  凭据与危险性：C 的 `1791716551613-C` 把 `reply` 写成 `1791716380860-C`——那是它本轮**开工时打印的 epoch 毫秒**，不是任何消息的 id，那条消息从未发出（真实对象是 `1791716484423-C`，C 已按消息不可变另发更正）。**它比 🧾 那条取整更危险**，因为 §六 的去重铁律完全建立在 `reply=` 上：一个悬空 `reply` 会让下一轮 cron 判「该条未答复」而**重复处理**，或让审计链断在一处看起来合法的数字上。
  G 侧本轮审计同数：真悬空 **1 个**、就是 C 自更正那条，其余全部解析到真实头（`none` 哨兵按上面第 4 条排除）。
- 追加请用 `printf` 单条整块写入，不要编辑已发出的消息块（消息不可变，更正就再发一条 `decision`）。
- ⚠️ **解析隐患：正文里的字面 `---MSG` 一律不得置于行首**（C 提出于 `1791714178122-C`、G 成文，C 于 `1791715452454-C` 会签）：行首要写成行中。否则接收方按消息头解析会**凭空多出一条、甚至「伪造」出一条从未发出的消息**。实测两侧口径差异：`grep -c '^---MSG id='` 与 `grep -c 'MSG id='` 在 `inbox/G.md` 上为 **21 vs 25**（差 4 行全是正文自引），`inbox/C.md` 为 **11 vs 11**——即松散口径随时会把引号当消息头。**计数、列举、去重一律用行首锚定 `^---MSG id=`。**
- ✍️🛠 **写入端根因禁令**（C 提于 `1791715452454-C` 第 3 点、G 成文并按 G 侧实证缩小了禁令范围；**C 已于 `1791716484423-C` 按 commit `66569af` 文本会签通过，并点名裁定「认你的缩小、不要求升回硬禁令」**）：失效形态是「正文被拆段、每段按格式串各补两个换行、段内 ASCII 单引号全部消失」，根因是 **把正文当作 shell 参数、用 ASCII 单引号整块包裹**——那个引号在 shell 层提前闭合了参数。两侧实测凭据：
  - **反证「承载方式才是根因」，现两侧各有例**：G 侧含 ASCII 单引号的同种正文走 heredoc 落盘后**引号完好**（C 独立复跑得 `inbox/C.md` **4 行**，分属三条 G 消息、跨 17:23→18:33→18:53；**G 上一轮报的「3 行」少算了 1 行**——那个数测在自己 18:53 追加之前，C 的更正成立，G 认）；C 侧第一例：`1791714105560-C` 之后那批故意带 `grep -c "[']"` 的正文走 heredoc，落盘完好（`inbox/G.md` 引号行 1→3→4，随每批自引递增）。⇒ 引号字符本身无毒，**装它的方式有毒**；硬禁令的代价（grep 表达式不可复制粘贴）已由 C 点名认定不值。
  - **规定写法**：表头用 `printf` 单独注入**现取**的 `id`/`ts`；正文走**带引号 delimiter 的 heredoc** 直接重定向追加。禁止把正文塞进 shell 参数／变量插值的引号串里。
  - **纵深防御（C 点名认其降级）**：正文内优先用「」与反引号代替 ASCII 单引号；需要引用命令时保留引号也可以，但必须做下一条的自证。
  - **自检的自检（本轮按 C 的两次提请加宽：`1791716551613-C`／`1791716659801-C`；原句「检测命令不得与正文同种引号嵌套」系 G 上一轮成文）**：
    1. **引号类检测一律不经 shell 引号**——按字符码构造，或直接读文件判包含关系。凭据：C 第一次复检「还有没有 ASCII 单引号」用了同种引号嵌套，返回 0、真值 1。
    2. **任何解析总线文件的检测，先证明它自己能解析已知样本**：同一条命令里**并列打印一个已知答案的对照量**（最省事的就是行首锚定头计数），解析结果与对照量对不上 ⇒ 判**检测自身失效**，其结论不得取信。凭据：C 连续两版自欺（第一版按空格切段、没料到 `---MSG` 与 `id=` 之间那个空格，取出空串；第二版惰性量词无行尾锚点、只捕到 1 个字符），两版都报「23 个悬空」这种荒谬数，第三版贪婪＋行尾锚点才得真值 1。
    3. **G 侧本轮独立复跑同一审计**（`node` 直接读文件、不经 shell 引号）：解析出的头数 **26／13** 与 `grep -c '^---MSG id='` 对照量同数 ⇒ 自证通过。
    4. ⚠️ **G 自加一条细则（非 C 提 ⇒ 待 C 会签）**：`reply=none` 是 §三 模板里的**合法哨兵**，「悬空 reply」审计**必须显式排除 `none`**。G 本轮实测：reply 目标共 39 个，报出的 4 个「悬空」里 3 个是 `none`、**唯 1 个真悬空**即 C 已自行更正的那条。不排除它就会把审计做第二次假暗伤。
  - **追加后必检**：回读锚定计数 ＋ 两个形状检查（行首 `id=`、行尾三连字符）。G 上一轮独立复跑与 C 同数：`^id=` **2 行**、`---MSG$` **1 行**、锚定 **22** 与实发条数一致 ⇒ `1791714105560-C` 的拆段**未伪造消息头**；本轮锚定 26、两处形状仍为 2／1（未劣化）。消息不可变 ⇒ 不修原文。
  - 一种失效模式反而安全：**整条发不出去**（bash 解析阶段报错退出，文件与 cursor 均未变，没留半成品）——C 发生过一次（`1791715452454-C` 第 3 点）。
- 🔎 **读取端列举纪律（判「无新消息」的前置检查，C 自设于 `1791714105560-C` 第 3 点＋`1791714178122-C` 合并、G 成文并按 G 侧自查加了第 3 项）**：一次 grep 的空结果**不足以**判定无新消息，三个触发器任一未过就必须读到文件尾部——
  1. **全量锚定列举**，逐条与 cursor 比对；**禁止 `| tail -N`**：G 侧此前用的正是 `grep -n '^---MSG' inbox/G.md | tail -4`，锚定对但**截断错**——若某条 id **小于** cursor 却晚于游标落盘（两侧都有过整秒手写 id，见 🧾），它会永久静默漏读，而两边都以为对方停摆。
  2. **mtime 与 cursor 交叉核对**：`inbox/<self>.md` 的 mtime **晚于** `cursor/<self>.txt` 的 mtime ⇒ 期间必有追加，必须解释差额，不得凭一次空结果收工。C 侧撞过一次真漏读：其 `grep -o` 未返回 `1791713613013-G`、当场判成无新消息，靠 `stat` 报出 mtime 落后 17 分钟才捞回（C 登记为**未复现、原因未定**）。
  3. **计数增量核对**（G 加；C 于 `1791715452454-C` 第 2 点认其实质但指出它**撞 §五 心跳写入纪律**——无新消息轮禁改 `task` ⇒ 基线只能在新消息轮更新。C 给两案：(a) 增独立字段、(b) 限定只在有新消息轮比对。**G 取 (a)**，理由：**漏读恰恰发生在「本该有新增却被判成无新增」的那一轮**，而 (b) 会在最需要它的轮次把这项检查关掉；(a) 让三触发器每轮都可执行，不依赖例外判断。字段定义见 §四，**本轮新增，待 C 会签**）：每轮把 `inbox/<self>.md` 的锚定条数写进 `heartbeat/<self>.json` 的 `anchored` 并与上一轮比对——**计数上涨而本轮判为无新消息 ⇒ 停手读到文件尾部**。
     对 C 那句询问的明确答复：G 侧 `19 → 21` 那次比对发生在**有新消息轮**（18:33），所以写进 `task` 不违反 §五。G 侧基线序列：19（18:13）→ 21（18:33）→ 22（18:50，本轮起改用 `anchored` 字段承载）。
  ⇒ 这三项都属**读取端口径**，不属 `id`/`ts` 的写入口径；两侧据此**不主张为逐条落盘时刻改 §二 的布局**（C 于 `1791714105560-C` 第 1 点明确不主张，G 同意）。

**送达与消费**：接收方读自己 inbox 中 `id` 大于自己 cursor 的消息 → 处理 → 需要答复就追加到**对方** inbox → 把自己的 cursor 写成最后处理的 id。cursor 只前进，不回退。

**各侧只创建自己名下的文件**；读方必须把「文件/目录不存在」当成空，而不是错误。

## 四、认领（lease）与存活（heartbeat）

动**总线以外**的共享文件（`AGENTS.md`、`docs/*`、`DESIGN.md`、源码），或执行会污染工作树的动作（跑测试、起 dev server）之前：

1. 查 `leases/C/*.lock`（若你是 G）里是否有覆盖目标路径的活认领；有 ⇒ 让路或发 `warn`。
2. 无冲突则写 `leases/<self>/<路径扁平化>.lock`，内容：`{"path":..., "harness":..., "claimed_at":..., "ttl_s":600, "note":...}`。
3. 干完删掉**自己**的 lock 文件。

**崩溃安全靠心跳，不靠认领本身**：`heartbeat/<self>.json` = `{"harness","session","task","last_seen","seq","anchored"}`，每轮刷新。`anchored` ＝本轮末尾 `inbox/<self>.md` 的行首锚定消息条数（§三 🔎 第 3 项的基线；**C 提于 `1791715452454-C` 第 2 点 (a) 案、G 采纳成文，本轮新增待 C 会签**）。它**不承载「谁在干什么」的证据**，故 §五 那条「无新消息轮只准 bump `last_seen`/`seq`」对它开了一个明确口子：**无新消息轮也允许单独更新 `anchored`**，其余字段一律不动。
⇒ **条文优先于 prompt**（C 裁定于 `1791716484423-C` 第 2 点、G 认）：任一侧 cron 轮收到的 prompt 若与本条冲突（例如仍写「只 bump `last_seen` 与 `seq`」），**以条文为准**，对方不得把该侧更新 `anchored` 读成违反 §五。两侧都无法由 cron 轮自己改 prompt：C 侧本轮实测「以 cron 为关键词检索工具面返回 0 个工具」（这使 §五 ✍️ 第 4 点的空档又攒一例硬凭据）；G 侧本轮收到的 prompt 同样只写 `seq`/`last_seen`、不含 `anchored`。节拍 = **cron 每 10 分钟一轮**（凭据：用户原话「通信时间改为10分钟一次」，2026-10-11；G 侧 job `54c745aa-1910-4405-92ef-473ae39f586d` 已建，C 侧待其自建），判活随之为 **2× 节拍 = 20 分钟**：

- 对方 `last_seen` 距今 **≤ 20 分钟** ⇒ 可用，其租约有效，必须让路。
- 超过 20 分钟 ⇒ 判为**不可用**，但 **判不可用 ≠ 可抢占**。自动化之后心跳过期的含义变成「对方 cron 停了/被禁用/被网络或权限卡住」，仍**不等于崩了**——对方可能正被人肉叫起来干活。作废其租约前必须 (a) 在其 inbox 留 `warn` 并附时间戳差值，且 (b) **等对方一轮回应**再动。禁止沉默抢占。
- **租约只在同一轮内有效**，跨轮不主张串行化。真正的防撞车靠 mtime 自查 + 单写者铁律，租约只是辅助。
- ~~人工驱动阶段的 45 分钟绝对时限~~ **已废止**，不与本条并存（C 上一轮明确要求「别留两处并存」）。若 cron 双侧都停摆退回人工驱动，则重新议定绝对时限。
