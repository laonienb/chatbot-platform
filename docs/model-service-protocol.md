## 1. 边界铁律（继承设计红线，验收时逐条检验）

1. 模型服务**不得**认识 `user_id` / `conversation_id` / `persona` —— 任何接口出现即越界。
2. `cost_usd` 不可得时返回 `null` + `cost_status: "unknown"`，**绝不返回 0**。
3. 响应必须如实返回 `model_used` + `provider`，供平台账本归因。
4. 模型服务**无状态**：可随时重启、可多副本、不持有会话/记忆/账本。
5. 合规策略优先于调用方 `routing` 请求，调用方**不可放宽**。
6. 平台断开连接时，模型服务**必须中止上游请求**。
7. 协议版本不兼容时平台**启动即失败**（过渡模式的例外见 §8）。
8. 超时预算分层：模型服务内部上游超时 < 平台总超时。
9. 平台 mock 后端**不得**作为生产降级路径。
10. `persona:` 前缀的请求，模型服务**显式 400 拒绝**（Q7-B）。
11. **可重放性判定按「副作用性质三分」，不得按状态码段归类**（v1.5 新增，见 §17.4）：
    任何"失败能否安全重放/入幂等窗"的判定，必须区分为
    ① **无副作用**（本地拒绝、未送达）② **结果不明**（超时、流中断、已发起调用后的 5xx）
    ③ **确定性拒绝**（同输入必同拒绝）。三者行为不同，一刀切必错 —— 两轮评审各在
    相反方向上验证过这一点。

## 3. 服务间鉴权（补 §9.1-3 缺口）

| 项 | 规定 |
|---|---|
| 形态 | **静态 Bearer token**（`Authorization: Bearer <MODEL_SERVICE_TOKEN>`），v1 不引入 mTLS |
| 生成/存放 | 部署时生成（≥32 字节随机），经 env/密钥管理注入双方；**不落库、不进 git** |
| 网络边界 | 模型服务**仅集群内网可达，不暴露公网**；token 是纵深防御的第二层，不是唯一屏障 |
| 失败语义 | 401 + `code: "service_auth_failed"`（区别于上游凭证失效的 `upstream_auth_failed`） |
| 轮转 | 双 token 并行窗口（新旧同认）后吊销旧值；协议不规定机制，部署侧保证 |
| 演进 | mTLS / 短期凭证列为 v2 候选，v1 明确不做 |

## 4. 请求契约

### 4.1 Headers

| Header | 必填 | 说明 |
|---|---|---|
| `Authorization` | ✅ | §3 的服务间 token |
| `X-Request-Id` | ✅ | uuid，平台生成、贯穿两层日志，排障主键 |
| `Idempotency-Key` | ⚪ | 语义 = **窗口内去重**（窗口 ≥10 分钟，与平台现状对齐）；模型服务在窗口内对同 key 返回首次结果或 409，**不得**二次烧上游 |
| `X-Model-Service-Version` | ✅ | 客户端声明的协议版本（当前恒为 `1`） |

### 4.2 Body

```jsonc
{
  "model": "deepseek-chat",        // 真实模型名。"persona:" 前缀 → 400 invalid_request（红线10）
  "messages": [ { "role": "user", "content": "..." } ],
  "stream": true,
  "stream_options": { "include_usage": true },   // stream=true 时平台必带
  "temperature": 0.8, "top_p": 1.0, "max_tokens": 2048,

  "routing": {                      // 扩展命名空间；模型服务可忽略，但须在 capabilities 声明
    "allow_providers": ["deepseek", "qwen"],
    "deny_providers": ["openai", "anthropic"],
    "fallback": true,               // 是否允许降级到备用供应商/模型
    "max_cost_usd": "0.05"          // 单请求成本熔断上限（十进制字符串）
  }
  // ⚠️ trace 字段：v1 期间平台**不得发送**（§14.3 收编，v2 预留）。
  // 原设计允许 trace.tenant 作部署级不透明标签，但平台出网守卫已将其列入禁字段；
  // 为避免「协议允许、守卫禁止」的分叉，v1 明确禁发，待 v2 连同其合规约束一并启用。
}
```

**禁止字段**（出现即 400 `invalid_request`）：`user_id`、`conversation_id`、`persona`、
**`trace`（v1 期间）**、任何形如平台业务身份的字段。人格与记忆已融进 `messages` 内容，
模型服务不理解其语义。

**宽松解析**：双方对未知扩展字段一律忽略不报错（forward-compatible）；仅对本文标注
「必填」的字段严格。

### 4.3 合规否决（Q8-B）

模型服务持有合规硬策略（如「禁止境外 provider」）。`routing` 是调用方**意图**，
合规策略是**上限**：请求违反硬策略时返回
`403 + code: "compliance_denied"`，`error.message` 说明被否决的约束。
`routing.allow_providers` 放宽不了合规策略（红线 5）。

#### 4.3.1 出口真实性（egress attestation）（v1.7-澄清5 新增：架构师 B `ade58e6` 裁决 ＋ A 落文，协议 §28.4）

`MS_UPSTREAM_VENDOR`（§26.6-丙 第 4 项）的语义 ＝ **部署方对真实出口的声明**；其真实性
**由部署流程与审计保证，不由代码保证**。服务侧只做**最小一致性校验**（第 2 条），
它挡的是**误配**，**挡不住蓄意错填**——部署方完全可以把 `api.openai.com` 写进
`xiaomimimo` 的允许列表。故：

1. **A-1 之后，红线 5 对"真实出口"的保证是流程性的（procedural），不是代码保证的。**
   `_check_compliance`（`main.py:139`）的两条判定臂对平台真实流量都不触发（无前缀 model
   恒不命中前缀臂；平台不发 `routing` ⇒ allow 臂是死的），而真实出口由
   `MS_LITELLM_API_BASE` 决定、合规检查**从不读它**（A 2026-10-11 实测、B `ade58e6` 独立复现）。
2. **最小一致性校验**（服务侧／启动期／落在**既有**的 `_reconcile_upstream_vendor_with_compliance`，
   不新增执行点、不做请求期判定）：`MS_UPSTREAM=litellm` 且 **`MS_UPSTREAM_VENDOR_HOSTS`**
   （逗号分隔的**主机名后缀**允许列表，**谁声明谁举证**）非空时，解析 `MS_LITELLM_API_BASE`
   的主机名；**不匹配任一后缀 ⇒ 拒绝启动**，报错须**同时打印** `vendor` / `api_base` / 允许列表三者。
   该 env **未声明 ⇒ 只 WARNING**（与 vendor 未声明同口径，避免打挂旧部署），文案**必须**写
   「**出口未经主机名校验**」。
   ⚠️ **`api_base` 为空的边界（A 补）**：`api_base` 为空 ＝ 走 litellm 自己的默认出口——那是
   **最不可控**的一条路 ⇒ `MS_UPSTREAM_VENDOR_HOSTS` 非空而 `api_base` 为空时，**同样按"不匹配"
   拒绝启动**（无法校验即按不通过处理，**不得静默放行**）。
   > **与 A1-4 是同一节口径的两面**（派单补件 `d2e908b`／总线 `1791736152729-C` 第 1 点要求"别分成两处"）：
   > §26.6-丙 **A1-4** 管的是「**声明的供应商名**是否命中 deny」（`upstream_vendor ∈ deny` ⇒ 拒启动）；
   > 本条管的是「**声明的真实出口**是否与 vendor 自洽」（`api_base` 主机名不在 `MS_UPSTREAM_VENDOR_HOSTS` ⇒ 拒启动）。
   > 两者**落在同一个** `_reconcile_upstream_vendor_with_compliance`、**同一个**启动期、**同一段**报错风格，
   > 是**同一条臂的两面**——勿写成两套口径。
3. **不把「按 `api_base` 主机名判定 deny」写进协议**（架构师 B 三条理由，A 采纳）：主机名 → 供应商
   是一张**永不完整**的真值表（第三方聚合网关、企业出口 NAT/正向代理、境内镜像与加速域名、上游改名换域）；
   建在这张表上会同时产生假阳性与**假阴性（真出境判成合规）**，而**假阴性比现在的失明更危险**
   —— 它给出"已封死"的错觉、让人停止审计；且 `vendor` 与 `api_base` **都是部署方自填值**，
   一致性检查在逻辑上无法自证 ⇒ 那是**配置校验，不是合规控制**，写成合规条款会**高估**红线 5 的保证强度。
4. **服务如实自曝**：capabilities 加 **`egress_verified: bool`**（＝本次启动是否真的做了第 2 条的主机名校验），
   置于 `features.compliance_policies` 旁；平台启动自检读到 `false` ⇒ **WARNING 并记入启动日志**
   （**不拒启动**，避免打挂既有部署）。⇒ 「失明」从**默认静默**变成**每次启动都会被打印一次的状态**。
5. **出口治理 与 `compliance_deny_providers` 的调整权属用户/运营**（与 §26.3 的"最后一张牌"同一归属）；
   服务侧**不在配置里静默放宽**。

## 5. 响应契约（非流式）

```jsonc
{
  "id": "chatcmpl-...",
  "object": "chat.completion",
  "model": "deepseek/deepseek-chat",   // ★ 实际调用的模型串（model_used），非请求别名
  "choices": [ { "index": 0,
                 "message": { "role": "assistant", "content": "..." },
                 "finish_reason": "stop" } ],
  "usage": {
    "prompt_tokens": 120,               // 必须实测；无法实测见 §7 metering 规则
    "completion_tokens": 80,
    "total_tokens": 200,
    "prompt_tokens_details": { "cached_tokens": 64 },      // 有则必填 → 平台 cache_read_tokens
    "completion_tokens_details": { "reasoning_tokens": 0 } // 有则必填 → 平台 reasoning_tokens
  },

  "x_model_service": {                  // ★ 扩展命名空间（自研后必须；Proxy 期缺失，见 §8）
    "cost_usd": "0.000123",             // 十进制字符串；不可得时 null，绝不 0（红线2）
    "cost_status": "exact",             // exact | estimated | unknown
    "provider": "deepseek",             // 实际供应商 → 平台 usage_logs.provider
    "model_requested": "deepseek-chat",
    "model_used": "deepseek/deepseek-chat",   // → 平台 usage_logs.model_upstream
    "fallback_used": false,
    "upstream_latency_ms": 812,
    "cached": false                     // 模型服务侧缓存命中
  }
}
```

### 5.1 平台侧消费规则（Q1-B 优先级链，账本落库口径）

| `x_model_service` 状态 | 平台行为 |
|---|---|
| `cost_status: "exact"` | 采信 `cost_usd` 为上游成本，`metering_source=provider` |
| `cost_status: "estimated"` | 采信但账本 `needs_review=true` |
| `cost_status: "unknown"` / `cost_usd: null` / **字段整体缺失**（Proxy 期） | 回落平台价格表推算；价格表也查不到 → `(0, needs_review=true)` 进对账清单。**绝不把 unknown 当免费。** |

token 计量沿用现有 `metering_source` 三档（provider / tiktoken / estimated）与
`needs_review` 联动，不改语义。

**两条独立路径，不得混淆（对 §9.1 评审洞 #2/#3 的契约级封堵）**：

- `cost_usd` **只替换 upstream 一侧**（毛利监控的 `cost_upstream` 来源）。用户扣费
  （billed，积分）**始终走平台 `rating_rules` 费率快照**，与 `cost_usd` 无关 ——
  照「pricing.py 退化为读 cost_usd」的字面实现会把用户按上游成本价扣积分、废掉
  零售与毛利模型，**禁止**。
- `metering_source` 记的是 **token 计量来源**，不是成本来源。平台账本须新增
  `cost_source` 列（`service_exact | service_estimated | price_table | none`，
  S6 实施），否则分不清「Proxy 过渡期本来没有」与「provider 漏报」。

## 6. 流式契约（SSE）

1. 逐块 `data: {OpenAI chunk}\n\n`，正常结束以 `data: [DONE]` 收尾。
2. `stream_options.include_usage=true` 时，**`[DONE]` 前必须有一个携带完整 `usage`
   的 chunk**（choices 为空数组）。平台现有 `stream_chunk_builder` 路径据此拼回实测 usage。
3. **终止事件（Q4-B，自研后必须；Proxy 期无）**：usage chunk 之后、`[DONE]` 之前，
   发一个独立命名事件承载扩展字段：

   ```
   event: model_service
   data: {"x_model_service": { ...同 §5... }}
   ```

   不污染 OpenAI chunk 结构；不认识该事件的客户端自然忽略。
4. **心跳**：`: keepalive` 注释行（推理模型长思考防中间层断连）。
   **v1.7-澄清5（架构师 B `ade58e6` ＋ A 落文，协议 §28.2）**：对 **reasoning 型上游**，「允许」升为
   「推理期间**必须发**」——**发送方 ＝ 模型服务**；触发条件 ＝ 收到一个**不产出正文**的上游 chunk
   （reasoning-only）时发一行，**不必按固定周期**（密度随上游产出节奏），同一次产出**兼作** §8.1
   首 token 计时的复位信号。**心跳不得进入终态缓存**（§8.2.2-3：否则会被流式终态重放缓存并重放、
   污染 `MS_IDEMPOTENCY_CACHE_MAX_CHARS` 的体积核算）。
   平台侧**必须忽略**一切注释行与未知命名事件（宽松解析）。本轮**只做内层**（服务发、平台仍吞，
   `remote.py:579`）——对外透传/自发属**对外字节流变更**，须另走 `AGENTS.md`「三」通告（§28.2）。
5. **取消传播（红线 6）**：平台断开 TCP → 模型服务必须立即中止上游请求。
   验收测试见 §10-T6。中止后已产生的 token 如何上报：连接已断，无法回报——
   由平台侧按现有 `abandoned` 对账路径收编（预扣估算），模型服务侧只记日志。
6. **收尾 chunk 必须携带 `finish_reason`**（v1.6 补，解缺口 N）：内容 chunk 的
   `choices[0].finish_reason` 为 `null`，**最后一个 chunk（其 `delta.content` 允许为空，
   v1.7 措辞更正 —— OpenAI 实际语义中携带 `finish_reason` 的 chunk 通常 delta 为空）
   必须携带非 null 的 `finish_reason`**（`stop` / `length` / 上游实际值），且位于
   usage chunk **之前**，与 OpenAI 流式语义一致。平台据此归因「正常结束 vs 被 `max_tokens` 截断」（工作单 P1-1），
   平台侧解析已就位（`remote.py` 从 chunk 提取），**服务侧不发送即静默失效**。
   ⚠️ 这是两侧桩的既存分歧点：平台桩已发、模型服务桩未发（§18.2-F1）。
7. **流式错误语义**（v1.6 补，解缺口 O）：SSE 一旦已开始写出（HTTP 200 已发）便无法
   再改状态码，故错误按「**首字节是否已发出**」分级：
   - **首字节之前**（尚未向客户端写出任何事件）→ **必须**返回 **HTTP 错误状态**
     （同 §7 表：429 / 504 / 502 …），**不得**以「200 + 流内错误帧」代替。
     否则平台的限流退避、`Retry-After` 透传、熔断计数**全部失效**。
   - **首字节之后**（部分内容已产出）→ 以**流内错误帧**收尾：
     `data: {"error": { …§7 错误体… }}`（无 `event:` 名，与 OpenAI 一致），随后关闭流。
     平台**必须**识别该帧：按 `error.code` 归因并**按 §11 判定是否计入熔断**，**不得**当作
     「正常结束」结算；已产出的部分内容按 **§8.1.1** 口径按已收 token 结算。
     > ⚠️ **"计入熔断"不是"一律计入"**（v1.6 补充说明，消除本项与 §11 负列表的表面冲突）：
     > 「是否计熔断」由 **`error.code` 经 §11 与实现既有的 code→计数映射**决定，**不由
     > "是不是流内错误帧"决定**。故流内 `rate_limited`／`budget_exhausted` 帧**不得**计熔断
     > （否则重复限流会误杀整条链路，正是 §11 负列表要防的），而流内
     > `upstream_timeout`／`internal_error`／`upstream_error` 帧**必须**计入。
     > 平台已有该映射（`remote.py` 的 `_CODE_TO_PLATFORM`），流式路径**复用**它即可，
     > **不得**另写一套"流内帧一律计数"。工作单 P1-9 已按此细化验收③（两个方向都要有用例）。
   - 例外：对端**断开连接**（红线 6）不产生错误帧，按本节第 5 条由平台 `abandoned`
     对账收编。
   - **平台对客户端的形态**（v1.7-澄清3 交叉索引）：平台把本节错误帧**同形**转发给客户端
     （`data: {"error": {…}}` 其后仍 `[DONE]`），退避时长走 `error.retry_after_s`。
     该对外接口属「平台↔客户端」，**不在本协议正文范围**，由 `AGENTS.md`「三」通告治理。
   - **实现现状（v1.7-澄清3 更新）**：v1.6 撰写时两侧均未实现（证据与缺口见 §18.2-F2）；
     自服务侧 `25c4bab` + 平台侧 `a639446` 起**已闭合**，验收见 §22。

## 7. 错误契约

统一 OpenAI 错误体，**`code` 机器可判是唯一分派依据**（内部协议不依赖 header 有无）：

```json
{ "error": { "message": "...", "type": "...", "code": "rate_limited", "param": null,
             "retry_after_s": 30 } }
```

**`retry_after_s`（可选，整数秒，v1.7-澄清2 新增加法字段，解 P1-9 预审缺口 ⑦a）**：
`rate_limited` 等临时性拒绝的建议退避时长。HTTP 层错误**同时**使用 `Retry-After`
响应头（两者并存时以 header 为准）；**流内错误帧没有 HTTP header 可携带**，
`retry_after_s` 是流式路径传递退避时长的**唯一**手段——平台识别后按 §7 对外映射
透传给客户端。缺省时客户端按自有策略退避。加法字段，旧客户端忽略即可，不升线协议版本。

| HTTP | `code` | 平台动作 | 备注 |
|---|---|---|---|
| 400 | `invalid_request` | 不重试，报错 | 含红线 10 的 `persona:` 前缀拒绝 |
| 401 | `service_auth_failed` | 不重试，**运维告警** | 服务间 token 错（§3） |
| 401 | `upstream_auth_failed` | 不重试，**运维告警** | 模型服务侧 provider 凭证失效 |
| 403 | `compliance_denied` | 不重试，提示不可用 | 合规否决（§4.3） |
| 404 | `model_not_found` | 不重试；触发目录重新同步（§9） | |
| 413 | `context_length_exceeded` | 不重试；平台侧上下文窗口策略问题 | |
| 429 | `rate_limited` | 不重试；`Retry-After` **透传**给客户端，由客户端退避 | 上游/模型服务限速，临时 |
| 429 | `budget_exhausted` | **不重试**；可选降级到便宜模型或拒绝用户 | 成本熔断/预算耗尽，窗口内无解 |
| 500 | `internal_error` | 不重试；计入熔断（§11），恢复靠 §8.4 降级链 | |
| 502/503 | `upstream_error` / `service_unavailable` | 不重试；计入熔断；可选降级 | |
| 504 | `upstream_timeout` | 不重试；计入熔断；可选降级 | 内部超时预算耗尽（§8.3）——**v1.7-澄清5 定义收紧**：**无任何上游 chunk**（含 reasoning-only）到达（§8.1） |
| 504 | `upstream_reasoning_timeout` | 不重试；计入熔断；可选降级 | **v1.7-澄清5 新增**（§8.1／§28.1）：到达**首个正文 token** 前超预算（**含推理时长**）⇒ 与 `upstream_timeout` **区分归因** |

> ⚠️ 「平台动作」列**不得**出现任何平台侧重试（v1.4 清理，见 §7.1）。本表原三处
> 「可重试」残留与 §7.1 硬规则冲突，已于会签后删除。

**平台对外契约的映射（Q5-B，加法演进）**：平台把上表翻译成对客户端的响应时，
`rate_limited` → 429 带 `Retry-After`；`budget_exhausted` → 429 不带 `Retry-After`
（兼容现有前端约定），**同时**在对外错误体新增 `error.code` 字段透传语义。
旧约定保留一个版本周期后废弃；该对外变更走 `AGENTS.md`「三」登记。

### 7.1 重试责任划分（审计定案 v1.3，解缺口 F）

原表按「可重试 1 次」描述，**未指明谁重试**，且让平台靠 HTTP 状态码推断可重试性——
这是设计缺陷（状态码不能表达"重试是否安全"）。定案如下：

**重试阶梯只有一级：模型服务对上游重试。平台对模型服务不重试业务错误。**

| 失败类型 | 谁重试 | 理由 |
|---|---|---|
| 上游瞬时故障（5xx/超时/连接错） | **模型服务**，内部重试（可换 provider，受 `routing.fallback` 约束） | 只有它知道上游的幂等语义与健康度；换 provider 是它的能力 |
| 模型服务自身故障（`internal_error`） | **不重试** | 立刻重试同一实例无意义；重试应由**平台熔断 + 降级链**（§8.4/§11）承担，不是逐请求重试 |
| 业务错误（400/401/403/404/413/429） | **不重试** | 重试不会改变结果 |
| **平台 → 模型服务的连接失败**（请求未送达） | **平台可重试 1 次** | 唯一安全的平台侧重试：请求未发出，无副作用。**必须**携带同一 `Idempotency-Key` |

**硬规则**：平台**只**在"已确认请求未送达"（连接建立失败/DNS 失败）时重试；
**收到任何 HTTP 响应后一律不重试**——因为 §8.2 的幂等窗口会让第二次请求直接命中
首次结果，重试毫无收益且徒增延迟。

**契约补充字段**：错误体可选 `error.retryable: bool`，语义 = 模型服务声明
「**重发同一请求是否可能得到不同结果**」。缺省 `false`。

> **完整定义（v1.7 定案，取代本节此前"发生在进入上游处理之前"的表述）**：
>
> - `retryable: true` ⟺ **重发同一请求可能得到不同结果，因此无需幂等窗保护**
>   —— 未送达 / 本地拒绝 / 上游**瞬时**拒绝（`429`、`503`）。
> - `retryable: false` ⟺ 落入两类之一：**结果不明**（可能已计费：超时、流中断、
>   已发起调用后的 5xx）或**永久性拒绝**（同输入必同拒绝：上游 `400/401/403/413/404`）。
>   两类**入窗结论相同、归因不同**，日志与 `error_code` 必须可区分。
>
> ⚠️ **为什么不能用"是否在进入上游处理之前"当判据**（v1.6 版表述的错误所在）：
> 上游 `413` 与上游 `429` **都**"被拒于推理之前、都无计费副作用"，但前者必须 `false`
> （同输入必同拒绝 → 入窗）、后者必须 `true`（重发可能成功 → 不入窗）。
> 两个候选判据（"处理前"与"有无副作用"）**对这两个反例给出相同答案**，因而都不可用作轴。
> 真正的轴只有「**重发是否可能得到不同结果**」。
>
> ⚠️ **该字段与状态码正交**：`413` 未必 `false`（本地 `persona:` 前缀拒绝也是 4xx 但属本地拒绝），
> `429` 未必 `true`（本地限流也返回 429 但同样是本地拒绝）。判定权在**模型服务**——
> 它才是唯一知道"这次失败是否已到达上游"的一方。

⚠️ **平台不依据该字段重试**（v1.4 会签改判，见 §14.2/§15.2）。按上面的硬规则，
平台永远没有"收到响应后重试"的时机，故该字段**不是重试开关**。它的**三个**用途：

1. **幂等入窗判定**（v1.5 新增，§8.2.1）：`retryable: true` ⇒ 不入幂等窗；
   `retryable: false` 且伴随上游调用 ⇒ 入窗。**这是它现在最实质的用途** ——
   模型服务是唯一知道"本次失败是否可能已计费"的一方；
2. 日志/可观测：区分"请求被处理前拒绝"与"处理后失败"（后者不可安全重放）；
3. 可透传进平台对外错误体，供**终端客户端**判断重试安全性。

**该字段与 HTTP 状态码相互独立**，不得隐含"仅 5xx 可能为 true"。例：模型服务自身
未就绪而**未发起**上游调用时，返回 503 + `retryable: true` 是正确的。

## 8. 超时 / 取消 / 幂等 / 过渡模式

### 8.1 超时预算分层（红线 8，审计重写 v1.1，解缺口 K/L）

原表述把"首字节超时"归给模型服务，但它实为**平台侧读超时**——分层实际只有一层。
重写为两侧各自独立的预算，**共同满足红线 8（内层 < 外层）**：

| 层 | 项 | 默认 | 归属 | 约束 |
|---|---|---|---|---|
| 平台 | 建连超时 | 5s | 平台 | |
| 平台 | **读超时**（任一 chunk 间隔） | 15s | 平台 | 保护"服务卡住不吐字" |
| 平台 | **流式空闲上限** | 90s | 平台 | 无**任何**字节（含心跳）超过此时长 → 断开并按 §8.4 降级。**心跳 `: keepalive` 可重置此计时**，故它不是"总时长"限制，而是"沉默时长"限制 |
| 模型服务 | 上游首 token 超时 | 15s | 模型服务 | **v1.7-澄清5 定义**：**上游任何 chunk（含 reasoning-only）** 都复位此计时；无任何上游 chunk → 504 `upstream_timeout`（此前实现成"首个**对外事件**"，reasoning-only chunk 不产出事件 ⇒ 实为"整段推理＋首个正文 token"预算，§28.1） |
| 模型服务 | **首个正文 token 超时** | 60s | 模型服务 | **v1.7-澄清5 新增**（§28.1）：从请求开始到**首个非空 `delta.content`** 的预算（**含全部推理时长**）；触发 → 504 `upstream_reasoning_timeout`（**与首 token 超时区分归因**）。保护"上游一直推理、始终不出正文"——首 token 行修正后**不再覆盖**该场景。⚠️ 默认值是**默认**不是**契约值**，部署侧可按模型族放大，但须守红线 8（见硬约束 2） |
| 模型服务 | **中途空闲超时**（chunk 间隔） | 30s | 模型服务 | v1.7-澄清2 补入（O1 定案）：首字节后任两个事件间隔上限，独立可配（`upstream_chunk_idle_s`，capabilities 必须暴露）；触发 → 流内错误帧 `upstream_chunk_timeout`（**归因区别于首 token 超时**） |
| 模型服务 | 上游总超时 | 60s | 模型服务 | **仅约束非流式调用**（v1.7-澄清2）：持续产 token 的流可合法超过 60s，流式由「首 token 15s + 中途空闲 30s + 平台绝对上限 180s」三层约束，不套用本行。非流式仍须 **< 平台读超时口径** |
| 平台 | **流式绝对上限** | 180s | 平台 | 单条 SSE 连接的绝对生存期，**心跳不可重置**（缺口 M，§15.4）。触发时按下方"超限收尾"处理 |

**三条硬约束**：

1. **平台侧不得依赖 httpx 的 total 超时保护流式**——流式响应总时长可远超 total，
   httpx 的 total 对流式不适用。必须显式实现"空闲计时"（缺口 K 的根因）。
2. **模型服务必须自持上游超时**，不得依赖平台断开兜底。模型服务的实际超时值
   **必须**在 `/v1/capabilities` 的 **`features.timeouts`** 暴露（**v1.7-澄清3 钉死嵌套层级**）：
   `timeouts: {"upstream_first_token_s": 15, "upstream_first_content_s": 60, "upstream_chunk_idle_s": 30, "upstream_total_s": 60}`，
   供平台启动时断言 "内层 < 外层"（T11 据此可自动化，而非人工读配置）。
   **v1.7-澄清5 增补**：新增 **`upstream_first_content_s`**（首个正文 token，§8.1 表／§28.1）；
   断言清单须**缺键即失败**——**不得**沿用"字段缺失即跳过"（那正是 P2-2 名义闭合、实则空转的成因）。
   ⚠️ **层级此前没钉死** —— §8.1 原文只写"暴露 `timeouts`"、§8.3 的形状示例里**没有**该字段，
   而真实服务放在 `features.timeouts` ⇒ 平台的启动断言只读**顶层**、再叠上"字段缺失即跳过"，
   红线 8 的「内层 < 外层」断言**对真实服务从未执行**（P2-2 名义闭合、实则空转，见工作单 P2-2 自我更正）。
   **规范位置 = `features.timeouts`**；平台可一并读顶层作**过渡容错**，但那不是可依赖的位置。
   **内层预算的对标对象取决于服务是否发心跳（v1.7-澄清5 修正 —— 这是 A 的首次裁定）**：
   服务**会**发心跳（capabilities `features.stream_keepalive: true`，§28.2）⇒ 平台**流式空闲上限 90s
   永不触发**（心跳持续复位它），真外层变成**绝对上限 180s** ⇒ 内层预算须 < **180s**；
   服务**不发**、或**声明位缺失**（按**保守侧**）⇒ 仍须 < **空闲上限 90s**。
   ⇒ 断言口径：**`upstream_first_token_s` / `upstream_first_content_s` / `upstream_chunk_idle_s`
   逐项 < 平台绝对上限（180s）；若 `stream_keepalive` 非 `true` 则还须 < 空闲上限（90s）**；
   `upstream_total_s` 仅非流式、按平台读超时口径（见下表第三行）。
   现行"三个预算逐项 < 90s"对**会发心跳的服务对标错了对象**（不改则两种误判：内层设 120s〔合法，<180s〕
   被断言拦下；或断言通过但流被 180s 砍断、归因成"上游超时"）。
3. **两个"总时长"概念必须实现为两个独立配置，不得合并**（§15.4-1）：

   | 概念 | 归属 | 语义 | 心跳影响 |
   |---|---|---|---|
   | `upstream_total_s` | 模型服务 | 单次**上游调用**时长上限 | 不适用 |
   | `model_service_stream_max_duration` | 平台 | 单条 **SSE 连接**绝对生存期 | **不可重置** |

#### 8.1.1 绝对上限触发时的收尾语义（§15.4-2，必遵守）

绝对上限触发时，SSE 响应头**早已以 200 发出**，无法再改状态码、也**不得**走 §8.4
的 503 降级路径。收尾动作：

1. **不得**改状态码或返回 503；
2. 立即关闭 SSE 流（发 `[DONE]` 或直接断连）；
3. **已产生的部分内容照常落库**，账本按**已收 token 结算**（不是 `failed`）；
4. 计入熔断（§11，属 5xx/连接错类）；
5. 记录 `error_code = stream_max_duration` 便于归因。

**用户侧表现为"回复中断"**，而非错误提示——与断流（红线 6）语义一致。

> 为何需要绝对上限：空闲计时会被心跳重置，不合规/故障的服务只要每 <90s 发一个
> `: keepalive` 即可无限期挂住连接（慢速资源耗尽）。启动断言只约束**合规**实现。


### 8.2 幂等

`Idempotency-Key` = 窗口内去重（≥10 分钟）。平台现状（`chat.py`：显式 header
不加窗口 / 无 header 用 `api_key+model+消息体` 指纹带 10 分钟桶窗）在平台侧生成
key 后**必须**通过 header 传给模型服务，保证「平台重试 ≠ 上游双烧」。

> ⚠️ **幂等窗对「流式」与「非流式」同等适用**（v1.7 定案，解 G2）：
> 本节的入窗与回放规则**按副作用性质分类，与传输形态无关**。实现**不得**以
> "流式回放不便"为由单方面把流式请求排除在窗口之外——那不是协议给的自由度，
> 而是**未写明的范围收缩**（S3 曾以 `main.py:114` 注释自缩，已证伪，见 §19.2）。

#### 8.2.1 入窗判定：按「是否伴随上游调用」而非按状态码类别（v1.4 会签补入）

**幂等窗口只允许「未到达上游」的失败不入缓存。**

判定标准**不是**状态码段，而是下面这张三分表（v1.5 修订，§16.3 并入 —— 原 v1.4
版本把"来自上游的 429"划入入窗侧，构成实质缺陷，见下方"为什么不能一律入窗"）：

| 情形 | 是否入窗 | 理由 |
|---|---|---|
| 成功响应 | ✅ 入窗 | 常规回放对象 |
| 上游调用**结果不明**（超时、流中断、已发起调用后的 5xx） | ✅ **必须入窗** | **可能已计费**，重发即双烧 —— 入窗要保护的核心场景 |
| 上游**永久性拒绝**（确定性拒绝；如 `413 context_length_exceeded`、上游 404、上游 400/401/403） | ✅ 入窗 | 同输入必同拒绝，回放结果正确且省一次上游调用 |
| 上游**瞬时拒绝**（`429` 限速、上游 `503` 未就绪） | ❌ **不入窗** | 未处理未计费 → 无双烧风险；重发**可能成功**，入窗会堵死退避恢复 |
| 本地拒绝（400 校验 / 401 服务间鉴权 / 403 合规 / **本地** 429） | ❌ 不入窗 | 无副作用 |
| 连接未建立 / DNS 失败 | ❌ 不入窗 | 请求未送达 |

> ⚠️ **"永久性拒绝"不按状态码白名单定义**（v1.6 澄清，见下）。`413` 与上游 `404` 是
> **常见实例，不是判据**——判据是"同输入必同拒绝"这一性质。若把本行读成
> `status in (413, 404)`，则上游 `401`（凭证失效）／`403`（内容策略）／`400`（请求非法）
> 这类**同样是永久性**的失败会被判为不入窗：它们已到达上游、重发必然同样失败，
> 不入窗只会让窗口期内每次重发都白打一次上游。

**入窗判定的实现开关是 `retryable` ＋「是否到达上游」两个布尔，不需要状态码**
（闭环 §7.1/§8.2.1）：模型服务是唯一知道"本次失败是否可能已计费/是否已到达上游"的
一方，故判定权交给它、用已有字段声明即可：

- `retryable: true`（失败发生在进入上游处理**之前**，无副作用）⇒ **不入窗**；
- `retryable: false` 且**已到达上游** ⇒ **入窗**。

> ⚠️ **不要实现成 `status in (413, 404)` 的白名单**（v1.6 澄清）：那样虽能通过
> 针对 `413` 的契约测试，却会漏掉上游 401/403/400 这类**已到达上游的永久性拒绝**。
> 上表第三行的判据是**性质**（同输入必同拒绝），状态码只是举例。**判据与状态码正交**
> ——这与 §7.1 对 `retryable` 的既有规定（"与状态码正交"）是同一条原则的两次体现。

上游 429 / 上游 503 应标 `retryable: true`；超时、流中断、已发起调用后的 5xx、以及
**已到达上游的永久性拒绝（上游 400/401/403/413/404）** 标 `false`。
**平台侧无需理解这张表，只需透传字段**；S3 按字段语义实现入窗。

**在飞位的释放义务（v1.7-澄清4：B 提案 §24.3 ＋ A 会签 §25）**：上面的 `retryable`/
入窗判据管的是"**要不要缓存**"；与之并列的另一条硬义务是——**在飞标记必须在请求终止的
任何路径上释放**（成功、已映射错误、以及**未预期异常**）。实现上应以 `try/finally`
或等价的 catch-all 保证「**先释放在飞位、后返回错误体**」。未释放导致同 key 后续请求得到
`409`，**视为违反本节**——§8.2.2-2 的在飞位语义是"**防同 key 并发**"，不是"永久拒绝"。

**为什么不能"按状态码段一刀切"**（两个方向都会错，v1.4 踩了后者）：

- **若"4xx 一律不入窗"**：`413` 会被排除。它虽是 4xx，但属**确定性拒绝**——
  同输入必同拒绝，入窗回放无正确性损失且省一次调用。
  ⚠️ 注意此结论**不依赖"413 是否已计费"这一未经验证的前提**（provider 普遍在推理前
  校验、通常不计费，但协议不建立在不可验证的假设上）。判据是"同输入必同拒绝"。
- **若"伴随上游调用一律入窗"**（v1.4 的错误）：上游 `429` 会被划入入窗侧 —— 而
  §7 已把恢复责任交给客户端（`Retry-After` 透传）。**实测后果**：平台兼容面幂等键 =
  `api_key+model+消息体` 指纹带 **10 分钟桶窗**（`chat.py:_compat_idem_key`，已核实
  `window = int(time.time()) // 600`），客户端退避后重发的请求**指纹不变 → 同一 key**
  → 模型服务**回放缓存的 429** 而非重新调上游 → 退避重试在窗口期内（最长 10 分钟）
  **必然失败**。瞬时限速被幂等窗放大成窗口级故障。且上游 429 意味着**未处理未计费**，
  入窗**零防双烧收益、纯有害**。
  （原生面不受影响：每次发消息生成新 `msg:{id}` 键；**AstrBot/QQ 走兼容面，是主路径**。）

**同时**，本地拒绝不入窗也是必需的（§14.2）：否则终端客户端在窗口期内重发同一请求，
会直接回放首次的 429/400，退避重试永远失败。

> 这是对 S3 实现方的**硬约束**，也是 T7 之外需补测的边界（见工作单 P1-7，含双向用例）。

**入窗「TTL 分类」（v1.7-澄清5 新增：架构师 B `ade58e6` 裁决，A 采纳，协议 §28.3）**

**不给 reasoning 型上游开入窗例外。** 两条理由：①「是否 reasoning 型上游」**不是服务侧可靠可判的输入**
（同一 model 有时推理有时不推理，且上游在超时那一刻**不会告诉我们**它正在推理）——把它当入窗判据
等于给本表加**第三维**，而这张表已因维度不清错过两次（§16.2「不该入窗的入了」、§19.2「该入窗的没入」）；
② 例外会**同时放掉真双烧保护**（首事件超时时上游很可能已在生成并计费，reasoning 型尤其如此，
A 实测 reasoning 106–194 tokens）。**入窗照入，动的是窗口长度**：

| 类 | TTL | 目的 |
|---|---|---|
| 成功响应 | `MS_IDEMPOTENCY_WINDOW_SECONDS`（默认 600s） | **回放正确答案**，需长窗口 |
| 「结果不明」类（首 token 超时、首个正文 token 超时、总超时、已发起调用后的 5xx） | **`MS_IDEMPOTENCY_ERROR_TTL_SECONDS`（新增，默认 60s）** | **防双烧**，不是回放答案；客户端抖动重发集中在**秒级**，600s 会把一次慢推理变成同一条消息的**窗口级锁死** |

> ⚠️ 60s 是**默认值、不是契约值**；且实现须保证 **error TTL < `MS_IDEMPOTENCY_WINDOW_SECONDS`**（否则"分类"无意义）。
> 落点：`_finish_window`（`main.py:283-299`）与 `_cache_stream_terminal`（`:253`）按 `should_cache` 分支选 TTL
> ——`IdempotencyWindow` 的 `expires_at` 已是**逐条**字段。

**连带项（架构师 B 第二次登记，A 采纳同批）**：回放在平台侧**不可识别**（`Idempotency-Replayed` 一类全仓
**0 命中**）⇒ **每次回放 504 都让平台再计一次熔断**（`_CODE_TO_PLATFORM` 中 `upstream_timeout` 第三位＝计数，
`model_service_cb_threshold=5`，`server/app/config.py:58`）⇒ **同一条消息重发 5 次即打开熔断、全站降级**。
短 TTL 把放大窗口从 600s 压到 60s，**但没有消除它**。⇒ 与本轮同批做（改的是同一段 `_finish_window`）。
**最小加法（A 定）**：回放时模型服务在**响应头**加 **`Idempotency-Replayed: true`**（流式与非流式都在响应头、
流式开流前已发出）⇒ 平台读到该头即**不计入熔断**（落点＝平台熔断计数处／`_CODE_TO_PLATFORM` 调用点）。
**不加 body 字段、不改 chunk 形状、不升线协议版本**；`retryable`/`code` 语义不变。

#### 8.2.2 流式的入窗与回放（v1.7 定案，解 G2 🔴）

**背景（已核实代码）**：S3 曾在 `msvc/main.py:114` 以注释把窗口范围缩到非流式，
导致**流式成功响应不入窗**。而流式成功**必然已调用上游、必然已计费**，按上文三分表
属「成功响应 ✅ 入窗」。后果是真实的**双烧**：兼容面幂等键 = `api_key+model+消息体`
指纹带 10 分钟桶窗（`chat.py:612` 流式路径同样调用 `_compat_idem_key`，已核实），
客户端（AstrBot/QQ 网络抖动重发）在窗口内重发同一请求 → 模型服务**真实重调上游、
二次计费**。与 §16.2 是同一暴露面、方向相反（那边"不该入窗的入了"，这边"该入窗的没入"）。

**定案**：

1. **入窗分类与传输形态无关**（承 §8.2 的告示）：流式终结态按同一三分法判定——
   - 流式**成功**终止、以及**已发起上游调用后**的流内错误帧终止（结果不明／已计费）
     → **必须入窗**；
   - **首字节前**的失败走 §6.7 的 HTTP 错误状态，按现有三分表判定（瞬时不入窗／
     永久性入窗），**不属于**本小节范围。
   - **不允许实现以注释自缩契约范围。**
2. **在飞位（`begin` → 409）语义对流式同样适用**——防止同 key 并发双流各自真实调用上游。
3. **SSE「回放」形态定为「终态重放」（折中并取代 19.2-2 的 (a)/(b) 二选一）**：

   > 命中窗口时，模型服务**以缓存的重放内容重新生成一条 SSE 流**：
   > 内容文本按缓存值分块发送，`usage`、终止事件、`[DONE]` 与首次一致。
   >
   > - **不要求逐事件原样重放**（不缓存事件序列）：**chunk 边界允许与首次不同**，
   >   但**内容文本、`usage`、`finish_reason`、终止事件必须一致**。
   >   理由：缓存事件序列会让窗口内存占用随生成长度无界增长；而缓存终态（一段文本 +
   >   一份 usage）是有界的。客户端（OpenAI 兼容层）关心的是内容与用量，不是分块切法。
   > - **不采用 409 显式拒绝**：那会把"重发失败"暴露给客户端，而兼容面客户端
   >   （AstrBot/QQ）重发正是幂等窗要吸收的正常行为；且 409 与"并发在飞"语义重叠，
   >   客户端无法区分"稍后重试"与"永久失败"。
   > - 缓存须有**条数/体积上限**；超限时的淘汰策略由实现决定，但**不得**在淘汰后
   >   静默重调上游——必须按 §8.4 降级或按未命中处理并由实现显式声明（写进 README）。

### 8.3 过渡模式（Q3-C 的关键补丁：Proxy 期无 capabilities 与红线 7 的冲突）

平台配置 `MODEL_SERVICE_MODE = proxy | native`：

| 模式 | 启动自检 | 成本口径 | 终止事件 |
|---|---|---|---|
| `proxy`（LiteLLM Proxy 过渡期） | **跳过** `/v1/capabilities` 自检；改为探活 `/health/liveness` + 用固定模型名调 `/v1/models` 确认目录可达。启动日志**必须**打「过渡模式：无成本/能力契约」警告 | §5.1 第三行（价格表回落） | 无，平台忽略缺失 |
| `native`（自研后） | **必须**调 `/v1/capabilities`；协议版本不兼容 → **拒绝启动**（红线 7 全额生效） | §5.1 全链生效 | 必须消费 `event: model_service` |

## 9. 模型目录同步

- 平台定期（建议 5 分钟）+ 收到 404 `model_not_found` 时即时，拉取 `GET /v1/models`。
- 同步产物写入平台 `llm_models` 的**纯展示属性**（可用模型集合、上游 id）；
  展示名/排序/启用/白名单仍是平台业务字段，不被同步覆盖（Q6-A）。
- 同步后平台侧不再需要 `llm_models.api_base` / `api_key` —— 凭证迁移到模型服务，
  平台注册表两列废弃（迁移由 S4/S5 执行，属后端 agent 范围，此处只定契约：
  **同步不携带任何凭证**）。

### 9.1 下线语义（审计补入 v1.1，解缺口 J）

上游**下架**模型必须被处理，否则平台目录保留一个已不存在的模型：用户可选中它 →
每次请求 404 → 每次触发一次注定无效的重同步（§9 首条），形成自我循环。

| 情形 | 平台行为 |
|---|---|
| 上游 id 在本次 `/v1/models` 中**消失** | 把对应 `llm_models` 行标为 `enabled=False`（**不删除**） |
| 该行是当前 `is_default` | 清除其默认标记，并按现有回退逻辑重选默认（平台已有该逻辑，见 `default_model_string`） |
| 该行有进行中的会话在用 | 由平台上下文处理（报 404 或引导换模型），协议不介入 |

**为什么标停用而不删除**：`llm_models` 行承载平台业务字段（展示名、排序、白名单、
历史引用）。删除会抹掉运营配置，且让"临时下架又恢复"变成人工重建。
**下线永不删除行** —— 这是契约，不是实现选择。

> 边界：同步**不得**因为上游消失而启用任何行，也不得改动平台的展示名/排序。

## 11. 平台侧熔断（§9.1-6，入 S4 验收）

- 对象：平台 → 模型服务的 HTTP 调用。
- 计数口径（S4 架构审计修订，2026-10-09）：**「连续失败」而非「滑动窗口内累计」**。
  原措辞自相矛盾（"滑动窗口内连续"），且连续计数是更保守选择：一次成功即清零，
  不会因长时间窗口内的稀疏失败累积误开。`threshold=5`。
- 计入的失败：**连接错误、超时（含首字节超时）、5xx**。
  ⚠️ 必须覆盖**流式读写路径**——流式是主路径，漏记等于熔断永不触发。
- **不计入**：4xx 业务错误（400/401/403/404/413/429），避免上游限流误杀整条链路。
- 状态机（半开语义必须明确，否则协议无判定标准）：

  | 状态 | 行为约束 |
  |---|---|
  | `closed` | 正常放行 |
  | `open` | **全部拒绝**，直接走 §8.4 降级路径（503 或可选直连） |
  | `half_open`（冷却期结束） | **限制放行**：每次只允许 1 个探测请求在飞；探测成功 → `closed`；探测失败 → 立即回 `open` 并重置冷却计时。**不得**在 half_open 下放行全量流量 |

  修订理由：原措辞只说"半开探测恢复"，未限定半开期的流量，实现可解读为
  "冷却期一过即恢复全量"，使熔断退化为固定 30s 屏蔽窗（失去了保护意义）。

### 16.2 新发现缺陷：「来自上游的 429」入窗会堵死客户端退避恢复 🔴

**条文冲突链**（三段各自成立、叠加矛盾）：

1. §7（v1.4）：`rate_limited` → 平台不重试，`Retry-After` **透传给客户端退避**——恢复责任在客户端；
2. §8.2.1 / P1-7：「伴随上游调用的失败 ✅ 入窗，**含来自上游的 429**」；
3. 平台兼容面幂等键 = `api_key+model+消息体` 指纹带 **10 分钟桶窗**（`chat.py` 现状）→ 客户端退避后重发**同一请求 = 同一 key**。

**后果**：上游 429 被缓存入窗 → 客户端按 `Retry-After` 退避重发 → 模型服务**回放缓存的 429**
而不是重新调上游 → 退避重试在窗口期内（最长 10 分钟）**必然失败**。瞬时限速被幂等窗
放大成窗口级故障。P1-7 的「为何同时要求不入窗」一栏其实已经写明了这个危害，但只对
**本地** 429 生效——上游 429 被表格划入了入窗侧，同样的危害没有消除。而 AstrBot/QQ
恰恰主要走兼容面指纹键，这是主路径。（原生面不受影响：每次发消息生成新 `msg:{id}` 键。）

**且上游 429 入窗没有任何防双烧收益**：限速拒绝意味着上游**未处理、未计费**，
重发不会双烧——入窗只有害处。

**事实备注（413，不影响结论）**：15.2-1 称 413「上游已处理并已计费」——存疑：主流
provider 的 context_length 校验拒绝发生在推理**之前**，不计费。但 413 是**确定性拒绝**
（同输入必同拒绝），入窗回放 = 省一次上游调用、无正确性损失，**维持入窗不变**。

### 16.3 修订条文（**§17 已确认，原样并入 §8.2.1 并同步工作单 P1-7**）

入窗的唯一目的：**防止同 key 重发导致上游再次被计费调用**。据此把「伴随上游调用的
失败」细分为三类：

| 情形 | 是否入窗 | 理由 |
|---|---|---|
| 成功响应 | ✅ | 常规回放 |
| 上游调用**结果不明**（超时、流中断、已发起调用后的 5xx） | ✅ **必须** | 可能已计费，重发即双烧 —— A 判据要保护的核心场景 |
| 上游**确定性拒绝**（413 上下文校验、上游 404） | ✅ 可入 | 未计费但重放结果必然相同，入窗省一次调用 |
| 上游**瞬时拒绝**（429 限速、上游 503 未就绪） | ❌ **不入窗** | 未计费无双烧；重发**可能成功**，入窗堵死退避恢复 |
| 本地拒绝（400 校验 / 401 服务间鉴权 / 403 合规 / 本地 429） | ❌ | 无副作用（v1.4 已定） |
| 连接未建立 / DNS 失败 | ❌ | 未送达（v1.4 已定） |

**与 `retryable` 字段自洽绑定（给该字段第三个用途，闭环 §7.1/§8.2.1）**：
模型服务是唯一知道「本次失败是否可能已计费」的一方，判定权交给它、用已有字段声明：

- `retryable: true`（失败发生在进入上游处理之前 / 无副作用）⇒ **不入窗**；
- `retryable: false` 且伴随上游调用 ⇒ **入窗**。

上游 429/503 应标 `retryable: true`（与 15.2-2 的 503 示例一致）；超时/流中断/已发起
调用后的 5xx 标 `false`。平台侧无需理解这张表，只需透传字段；**S3 实现方按字段自身

### 20.2 G2 的回放形态：改判为「终态重放」，不采用 19.2-2 的 (a)/(b) 原案

B 给的 (a) 事件序列回放 / (b) 409 显式拒绝，**两端各有一个实质缺陷**：

- **(a) 原样事件序列回放**：缓存体积**随生成长度无界增长**（一条 10 分钟窗口内的长回复
  要缓存完整事件列表），而窗口内可累积多条 → 内存风险不可控；
- **(b) 409 显式拒绝**：把"重发失败"**暴露给客户端**，而兼容面客户端（AstrBot/QQ）
  重发恰恰是幂等窗要**吸收**的正常行为；且 409 与"同 key 并发在飞"语义重叠，
  客户端无法区分"稍后重试"与"永久失败"。

**定案（写入 §8.2.2 第 3 条）**：命中窗口时**用缓存的终态重新生成一条 SSE 流** ——
内容文本、`usage`、`finish_reason`、终止事件与首次一致，**chunk 边界允许不同**。
理由：缓存**终态**（一段文本 + 一份 usage）是**有界的**，缓存**事件序列**是无界的；
而 OpenAI 兼容客户端关心的是内容与用量，不是分块切法。另加两条硬约束：
缓存须有条数/体积上限；**淘汰后不得静默重调上游**。

### 27.4 裁定：`MS_CATALOG_MODELS` 入库默认（R2）——**可执行一句话**

**为什么是对齐代码默认、而不是列单值**：
1. **目录是白名单（并集语义）**：多列一个无害、少列一个必 404 ⇒ 取并集不取交集。
2. **单值现状是一条反直觉缺陷**：`.env.example` 的**单值**会在装 compose 时被注入，使部署的目录**比不注入 env 直接跑还窄**（裸跑用代码默认两值、compose 只给一值）——「配了反而更少」。
3. **对齐代码默认 = 对齐「不注入时的行为」**，三处同值后改一处即改全部，消除漂移源（三处三个值本身就是缺陷源）。

**不把 `gpt-4o-mini` 列进目录**：它是**平台侧**回落默认（`llm_default_model`，DW-4 ② 实测），服务侧不该为一个平台内部默认值放宽自己的对外模型集，且它属 deny 供应商 `openai` 的命名域、出现在境内服务目录里语义也不对。正确修法是**平台侧**把 `llm_default_model` 指向目录内某个 id（或把同步插入的行 enable 起来）——不属本次入库默认。

**② 谁在哪一步启用「目标 model」**：
> **「目标 model」只有一个正确启用位 ＝ 该部署的 `MS_CATALOG_MODELS`（服务侧 env）；管理端 enable 管的是"平台选哪个模型"，不改变服务侧目录校验。**

理由：404 发生在**服务侧入站关口**（`main.py:174-178`），管理端点不动它。DW-4 ② 实测的正是这个错位（目录同步插入的行 `enabled=0` ⇒ 平台回落 `gpt-4o-mini` ⇒ 服务侧目录无它 ⇒ 开流即 404）。⇒ **两侧必须成对**：`MS_CATALOG_MODELS` 含该 id **且** 管理端把对应行 enable（或平台 `llm_default_model` 指向目录内 id）。README 应补一句这条成对要求。

**404 / 403 分辨：写进 README 排障一节（一句话），不进启动自检。** 理由：自检只能对账**启动期已知量**（vendor ∈ deny、超时分层），而"平台会发哪个 model"由**运行时**决定（平台可发目录内任意一个），服务侧启动时无从自检；但它是**最高频的运维误判**（404 看着像上游故障）。一句话口诀：

> **`404 model_not_found` ＝ 服务侧目录缺口（无前缀 model 不在 `MS_CATALOG_MODELS` 里），不是上游；`403` 只会来自合规 deny（显式发 `openai/…` 等前缀时；A-1 之后无前缀 model 不会命中）；到达上游之后的失败才带 §7 的上游 `code`。**
