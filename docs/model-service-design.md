## 0. 摘要（TL;DR）

**决定**：把"所有与模型相关的事"从聊天平台中剥离，成为独立的**模型服务**；平台通过一个
明确的 HTTP/SSE 协议调用它。平台不再直接接触任何 provider。

**协议**：复用平台**已经对外提供**的 OpenAI 兼容协议（`POST /v1/chat/completions` + SSE）。
不发明新协议。理由见 §3.1。

**边界铁律**（本文最重要的一句）：

> **模型服务永远不知道"用户"是谁，只知道"请求"。**

**必须坚持的三条硬约束**（每条都对应一个真实隐患，见 §5）：

1. 拿不到成本时返回**"未知"，绝不返回 0** —— 否则平台的毛利监控会静默失效。
2. 平台侧账本**同时记录**逻辑模型名与实际模型串 —— 否则用户投诉"回复变差"无法归因。
3. 模型服务必须**无状态、可水平扩展、可随时重启** —— 否则它成为全站单点。

**本文未决问题**：§9 列出 9 项，需要其他 agent 会商定案。其中 **Q1/Q2/Q3 是阻塞项**。

## 1. 背景与动机

### 1.1 现状（已实现，可核对）

| 事实 | 位置 |
|---|---|
| LiteLLM 以 **Python 库**形式内嵌在 server 进程，惰性 import | `server/app/llm/gateway.py` |
| 模型注册表 `llm_models` 存 `api_base` / `api_key`（**明文**） | `server/app/models/llm_model.py` |
| 模型解析：会话覆盖 > 人设偏好 > 注册表默认 > 环境默认 | `server/app/services/chat.py:142` |
| 凭证：注册表优先，为空回落 `.env` 的 `LLM_API_KEY`/`LLM_BASE_URL` | `server/app/llm/gateway.py:144` |
| `DESIGN.md` §10 与 `deploy/docker-compose.yml` 写了 `litellm` 服务，但**从未落地** | compose 注释："M1-M2 里程碑加入" |
| 无自动重试/降级：上游报错即结算为 `failed` 并扣费 | `server/app/billing/ledger.py` |

### 1.2 为什么要解耦

1. **境内合规**：数据出境控制需要一个集中的收口点。分散在平台各处无法审计。
2. **维护成本**：每加一个供应商/换一次端点，现在都要改平台库、跑迁移。
3. **成本真相**：真实上游成本只有"实际发起调用的一方"知道。平台靠价格表推算，
   遇到聚合商或被抽象的模型串就失真（见 §5.2）。
4. **可观测性**：模型层指标（缓存命中、降级次数、上游延迟）无法在平台侧获得。
5. **稳定性**：实测 `import litellm` 冷启动 **9.6s**（若 `LITELLM_LOCAL_MODEL_COST_MAP`
   未在导入前设置，会尝试远程拉价格表并 3 次重试）。解耦后平台可**完全不依赖**
   litellm 包，启动与部署都更干净。

### 1.3 已确认的前提

- 客户主要在**境内** → 主力供应商应为境内模型（DeepSeek / Qwen / GLM）+ 自部署；
  境外模型仅在具备合规路径时使用。
- 平台对外**已有** OpenAI 兼容层（`/v1`），被 AstrBot 等消费 → 协议有现成参考实现。

## 2. 设计原则

| # | 原则 | 说明 |
|---|---|---|
| P1 | **模型服务只做模型能力** | 路由、凭证、重试降级、成本、限流熔断、合规控制 |
| P2 | **平台只做业务编排** | 人格注入、记忆、会话、鉴权、计费账本、业务配额 |
| P3 | **不做隐式耦合** | 所有跨服务信息走显式协议字段，不靠数据库共享、不靠约定俗成 |
| P4 | **抽象用于路由，可观测性用于排障** | 允许逻辑模型名，但实际模型/供应商必须可追溯 |
| P5 | **失败要显式** | 未知就是未知（不返回 0）；降级要标注；不静默兜底 |
| P6 | **协议可演进** | 能力声明 + 版本协商，启动时自检而非运行时爆炸 |
| P7 | **一套代码，两种形态** | 模型服务可选独立进程或内嵌（见 §7） |

## 3. 架构

### 3.1 为什么复用 OpenAI 兼容协议

平台对外已经是这个协议（`/v1/chat/completions`，SSE，`data: [DONE]` 结束），
并被 AstrBot 消费。让模型服务**也说同一个协议**，收益：

- **一份协议、两个实现、一套契约测试**。平台的 `/v1` 是现成的参考实现，
  语义已被代码与测试钉死。
- 平台天然既是该协议的**服务端**（对客户端）也是**客户端**（对模型服务）。
- 将来替换模型服务（换供应商、自研）时，客户端一行不用改。
- 不引入第二套协议，避免"自己维护两套语义"。

> ⚠️ 关键边界：**模型服务只认真实模型名（`deepseek-chat`），不认 `persona:<slug>`。**
> 人格是平台的业务概念，渗进模型层就毁掉了边界。`persona:` 解析留在平台侧。

### 3.2 分层视图

```
┌──────────────────────────────────────────────────────────────┐
│  客户端：Web / AstrBot(QQ) / 小程序 / 第三方 OpenAI 工具        │
└───────────────┬──────────────────────────────────────────────┘
                │ ① 平台对外协议（OpenAI 兼容，JWT 或 API Key）
                ▼
┌──────────────────────────────────────────────────────────────┐
│  聊天平台（server）                                            │
│  · 用户/会话/消息/鉴权          · 人格注入、记忆、上下文窗口     │
│  · 计费账本、费率规则、钱包      · 业务配额（月度/订阅）         │
│  · persona:<slug> 解析          · 展示名/排序/用户可见性        │
│  ❌ 不含：provider 凭证、模型路由、成本计算、数据出境控制        │
└───────────────┬──────────────────────────────────────────────┘
                │ ② 内部协议（本文定义；OpenAI 兼容 + 扩展字段）
                ▼
┌──────────────────────────────────────────────────────────────┐
│  模型服务（model-service）                                     │
│  · provider 凭证与路由、重试/降级/超时   · 模型目录 /v1/models  │
│  · 计量与**成本归属**（cost）            · 缓存、A/B、影子流量   │
│  · 数据出境控制、PII 脱敏、日志脱敏      · 单 Key RPM/TPM、成本熔断│
│  ❌ 不含：用户身份、会话状态、人格、业务计费账本                 │
└───────────────┬──────────────────────────────────────────────┘
                │ ③ provider 原生协议
                ▼
   境内 API（DeepSeek/Qwen/GLM…） · 自部署（vLLM/Ollama） · 境外 API（合规前提下）
```

> ① 与 ② **协议同构但语义不同**：① 认 `persona:`、要 JWT、写业务账本；
> ② 只认真实模型名、用服务间凭证、只报事实（用量/成本/供应商）。
> 同构是刻意为之（省一套心智），但**不可混为一谈**——见 §9 Q7。

### 3.3 边界清单（写进协议，作为"什么不许放进来"的依据）

| 必须放模型服务 | 必须放平台 |
|---|---|
| provider 凭证、路由、重试降级 | 用户、会话、消息、鉴权 |
| 模型目录（`/v1/models`） | **人格注入、记忆、蒸馏** |
| 真实上游成本、token 计量 | 计费账本、费率规则、钱包 |
| 数据出境控制、PII 脱敏、日志脱敏 | 业务配额（月度额度、订阅权益） |
| 单 Key RPM/TPM、**成本熔断** | 展示名、排序、用户可见性/白名单 |
| 供应商选择、A/B、影子流量 | `persona:<slug>` 解析 |

**两个最容易越界的地方**：

- **人格、记忆、蒸馏绝不上移**。它们是平台的核心业务语义（见 `DESIGN.md` §13）。
  模型服务一旦开始"理解人设"，解耦即告失败。
- **配额要拆成两层**：平台管业务额度；模型服务管技术保护（限速、成本熔断）。
  好处：平台可以在模型服务返回**额度/成本类拒绝后降级到便宜模型继续服务**，
  而不是把用户直接拒之门外——这比现状（上游报错即失败并扣费）体验好得多。

## 4. 协议契约

> 本节是**待评审草案**。协议细节最终应独立成 `docs/model-service-protocol.md`
> （被两个服务同时消费），本文保留设计意图与理由。

### 4.1 端点

| 端点 | 用途 | 备注 |
|---|---|---|
| `POST /v1/chat/completions` | 对话（流式/非流式） | 主体，见 4.2 |
| `GET /v1/models` | **模型目录发现** | 平台同步到自己的展示目录；解决"人工填注册表导致漂移" |
| `GET /v1/capabilities` | **能力声明 + 协议版本** | 平台**启动时自检**，不兼容则拒绝启动（见 §5.5） |
| `GET /healthz` | 存活/就绪 | 区分 liveness / readiness |

> `GET /v1/models` 是当前**缺失**的能力：平台的 `llm_models` 靠人工填
> （`server/app/api/native/models.py:16` 的 `SEED_MODELS`），必然与实际可用模型漂移。

### 4.2 请求

沿用 OpenAI 字段，**新增平台所需信息的显式字段**（置于扩展命名空间，避免与
OpenAI 未来字段冲突）：

```jsonc
POST /v1/chat/completions
X-Request-Id: <uuid>              // 贯穿两层，排障必需
Idempotency-Key: <string>         // 防重试双烧（平台已实现此机制）
X-Model-Service-Version: 1        // 客户端声明的协议版本

{
  "model": "deepseek-chat",       // 真实模型名，不是 persona:<slug>
  "messages": [ { "role": "user", "content": "..." } ],
  "stream": true,
  "temperature": 0.8,

  // ---- 平台扩展：路由偏好（模型服务可忽略，但须在 capabilities 中声明支持）----
  "routing": {
    "allow_providers": ["deepseek", "qwen"],   // 合规/成本白名单，见 §5.3
    "deny_providers": ["openai", "anthropic"], // 境内合规：显式排除
    "fallback": true,                          // 是否允许降级
    "max_cost_usd": 0.05                       // 单请求成本熔断上限
  },
  "trace": { "tenant": "t-123" }               // 仅用于日志路由，非身份
}
```

**平台不发送**：用户 ID、会话 ID、人格内容、记忆内容（人格/记忆已作为 messages 内容
融进 prompt，模型服务无需理解其语义）。

### 4.3 响应（非流式）

```jsonc
{
  "id": "chatcmpl-...",
  "object": "chat.completion",
  "model": "deepseek/deepseek-chat",     // ★ 实际调用的模型串（非别名）
  "choices": [ { "index": 0, "message": { "role": "assistant", "content": "..." },
                 "finish_reason": "stop" } ],
  "usage": {
    "prompt_tokens": 120,
    "completion_tokens": 80,
    "total_tokens": 200,
    "prompt_tokens_details": { "cached_tokens": 64 }   // → 平台 cache_read_tokens
  },

  // ---- 扩展：成本归属与可观测性（本文核心，见 §5.2）----
  "x_model_service": {
    "cost_usd": "0.000123",        // ★ 十进制字符串；无法确定时为 null，绝不为 0
    "cost_status": "exact",        // exact | estimated | unknown
    "provider": "deepseek",        // 实际供应商
    "model_requested": "deepseek-chat",
    "model_used": "deepseek/deepseek-chat",
    "fallback_used": false,        // 是否发生降级
    "upstream_latency_ms": 812,    // 上游耗时（区分"上游慢"与"模型服务慢"）
    "cached": true                 // 是否命中模型服务侧缓存（如语义缓存）
  }
}
```

### 4.4 流式（SSE）

- 逐块 `data: {...}`（OpenAI chunk 格式），结束发 `data: [DONE]`。
- **末尾必须带 `usage` 的 chunk**（OpenAI 的 `stream_options.include_usage`）——
  平台侧 `gateway.py` 已用 `stream_chunk_builder` 从 chunk 拼回实测 usage，正好对接。
- **扩展字段的投递**：`x_model_service` 放在**最后一个 chunk**（含 usage 的那个）或
  独立的终止事件中，二选一，见 §9 Q4。
- **心跳**：推理模型可能出现长时间无 token。建议发 `: keepalive` 注释行，
  防止中间层空闲超时。平台侧须**忽略**该类事件（当作非内容）。

### 4.5 计量与成本契约（硬约束）

| 字段 | 要求 | 理由 |
|---|---|---|
| `prompt_tokens` / `completion_tokens` | 必须为**实测值**；无法实测时须标注 | 计费的命根子 |
| `prompt_tokens_details.cached_tokens` | 有则必填 | 映射平台 `cache_read_tokens`；缓存折扣已接进计价 |
| `cost_usd` | **十进制字符串**（非 float） | 与平台 `Decimal` + `Numeric` 的金额口径一致，避免浮点误差 |
| `cost_usd` 不可得时 | 返回 `null` + `cost_status: "unknown"` | **绝不返回 0**（见 §5.2） |
| `model_used` / `provider` | 必须如实返回 | 否则投诉无法归因（见 §5.4） |

**平台侧对应处理**：`cost_status != "exact"` 时，账本行标 `needs_review`，
并记入对账清单——**不得当成免费**。

### 4.6 错误契约

统一的 OpenAI 错误体：

```json
{ "error": { "message": "...", "type": "...", "code": "provider_rate_limited" } }
```

**`code` 必须机器可判**，因为平台要据此决定"重试 / 降级 / 拒绝 / 提示用户"。
这直接关系到已登记的对外契约（`AGENTS.md`「三」）：

| HTTP | `code` | 平台应做的 | 说明 |
|---|---|---|---|
| 400 | `invalid_request` | 不重试，报错 | 请求本身有问题 |
| 401 | `upstream_auth_failed` | **不重试，告警** | 模型服务侧凭证失效，需运维介入 |
| 404 | `model_not_found` | 不重试，提示模型不可用 | 应同步修正平台展示目录 |
| 429 | `rate_limited` + `Retry-After` | **可退避重试** | 上游或模型服务限流（临时） |
| 429 | `budget_exhausted` **不带** `Retry-After` | **不重试**，可降级/提示 | 配额或成本熔断（本月/本预算内无解） |
| 502/503 | `upstream_error` / `upstream_timeout` | 可重试/降级 | 上游故障 |
| 504 | `upstream_timeout` | 可重试/降级 | 明确超时 |

> ⚠️ **现状风险**：平台当前的对外契约里，限流 429 与配额 429 靠"是否带
> `Retry-After`"区分（见 `AGENTS.md`「三」）。这个约定**很脆弱**——一旦上游自己
> 带 `Retry-After`，语义就混淆了。**建议协议层面用独立 `code` 区分，不再依赖 header
> 的有无。** 这是本文对现有契约的一个改进建议（见 §9 Q5）。

### 4.7 超时 / 取消 / 幂等

- **超时预算分层**：平台设总超时（如 120s），模型服务内部设**更短**的上游超时
  （如 60s）+ 首字节超时（如 15s）。否则平台先超时断开，变成"钱花了、回包丢了"。
- **取消传播**：平台断开连接 → 模型服务**必须中止上游请求**，不能干等跑完。
  否则用户点了停止，token 照烧。平台侧已有 `CancelScope(shield=True)` 保证
  本地结算落库（`server/app/services/chat.py:472`），但**上游要真的停**。
- **幂等**：`Idempotency-Key` 语义需明确"窗口内去重"还是"永久去重"。
  平台侧现为：显式 header 不加窗口；无 header 用 `api_key+model+消息体` 指纹
  **带 10 分钟桶窗**（`server/app/services/chat.py:492`）。

## 5. 隐患与对策（本文重点）

> 每条都力求"能落到一个具体动作或字段"，而非泛泛而谈。

### 5.1 边界会失控（最高风险，且是"慢性"的）

"模型相关的业务都在模型服务中实现"是一句**没有边界的话**。压力之下（"这里顺便加个
判断"）它会稳步膨胀，最终模型服务里长出一个平台，耦合换个门进来。

**对策**：
- §3.3 的边界清单**写进协议文档**，作为评审依据。
- 建立一条可检验的规则：**模型服务的任何接口都不应出现 `user_id` / `conversation_id`
  / `persona` 字段**。出现即越界，评审时直接拦。
- 模型服务不得持有业务状态（会话、记忆、账本）。

### 5.2 成本不透明 → 毛利监控静默失效（最隐蔽）

平台靠 `cost_billed` vs `cost_upstream` 发现"费率配错了"
（`server/app/billing/monitor.py`）。若模型服务：
- **不返回成本** → 平台 `quote_upstream_cost` 查不到价，返回 `(0, needs_review=True)`；
- **不可得时返回 0** → 更糟：平台看到"零成本、全是利润"，**监控显示一切正常，而在无声亏钱**。

**对策**：
- 协议硬约定：`cost_usd` 不可得返回 `null` + `cost_status: "unknown"`，**绝不返回 0**（§4.5）。
- 平台侧：`cost_status != "exact"` → 账本 `needs_review = True` 并进对账清单。
- 选型建议：**成本口径由模型服务提供**（它才知道真实价），平台侧不再依赖
  litellm 价格表——这同时也是"平台彻底不依赖 litellm 包"的前提。

### 5.3 数据出境控制与"白名单"到底谁说了算

境内合规要求（见 §1.3）意味着模型服务必须能**按请求**约束可用供应商。
但"这个用户可以调哪些模型"是**业务授权**（平台的事），"这个模型能不能出境"是
**合规策略**（模型服务的事）。

**对策**：两者分离，协议上体现为两个不同字段——
- 平台发 `routing.deny_providers` / `allow_providers`（**业务授权**意图）
- 模型服务持有**合规硬策略**（如"租户 X 一律禁止境外 provider"），并有**否决权**：
  合规策略优先于平台请求，被否决时返回明确 `code`（建议新增 `compliance_denied`）。

**这条必须写死**：合规策略不能由调用方随意放宽。

### 5.4 模型串被抽象化 → 投诉无法归因

为解耦，很容易把所有请求统一成 `chat-default`。结果用户投诉"今天回复变差了"，
你查不出当时用的是哪个模型。

**对策**（P4）：**抽象用于路由，可观测性用于排障**。平台账本**同时记录**
逻辑模型名（用户可见）与 `model_used` + `provider` + `fallback_used`。
现有 `usage_logs` 已有 `model` 与 `model_upstream` 两列，正好承载——**无需改表**。

### 5.5 版本漂移（两个服务独立部署后必然发生）

模型服务加字段/改语义，平台没跟上 → **运行时**才炸。

**对策**：`/v1/capabilities` 返回协议版本 + 支持的特性集；
**平台启动时自检，不兼容则拒绝启动**（fail fast），而不是等第一个用户请求失败。
另建议平台侧对未知扩展字段**宽松解析**（forward-compatible），只对必需字段严格。

### 5.6 关键路径 +1 跳 → 可靠性可能不升反降

现在一次聊天过两跳。模型服务重启/超时/内存泄漏 → **全部对话能力归零**
（且平台已不装 litellm，连兜底都没有）。

**对策**：
- 模型服务**无状态**，可随意重启、多副本水平扩展。
- **明确降级策略**（§9 Q2 阻塞项）：模型服务不可用时，平台是 (a) 报 503，
  (b) 回落直连某个 provider（保留最小直连能力），还是 (c) 回落本地 mock
  （**仅开发环境，生产不可用** —— mock 会假装成功，对生产是灾难）。
- 平台侧对模型服务调用设**熔断**，避免雪崩式重试。

### 5.7 双份运维成本（与用户的解耦动机相冲突）

用户想要解耦的理由是"维护麻烦"，但**两个服务本身更麻烦**（部署、监控、日志、
版本、上下线顺序）。

**对策**：§7 的"一套代码、两种形态"——解耦是**架构上的**，不强制**部署上**两套。
等真需要独立扩缩容/独立升级时再拆开，中间无需重写。

### 5.8 计量口径分叉

如果模型服务也做配额/计量，而平台也做，两边数字会**对不上**（谁是真源？）。

**对策**：职责分离——模型服务报**事实**（tokens、成本、供应商），
平台是**账本真源**（收多少钱、扣多少积分）。模型服务的限额只作为**技术保护**
（防单 Key 刷爆），不是业务账本。对不上时以平台账本为准，模型服务侧数字仅用于熔断。

### 5.9 协议同构带来的语义混淆

① 与 ② 都是 OpenAI 兼容（§3.1），容易被误认为"同一个东西"，导致：
有人拿 `persona:<slug>` 去调模型服务，或把模型服务暴露给终端用户。

**对策**：
- 协议文档**显式声明**两者的差异（认不认 persona、用什么鉴权、写不写账本）。
- 模型服务**不暴露公网**（仅集群内网可达），对外只经平台。

## 7. 部署形态（一套代码，两种）

建议**同一代码库**，通过配置决定形态：

| 形态 | 适用 | 说明 |
|---|---|---|
| **A. 独立进程**（推荐目标态） | 生产 | 模型服务独立部署、独立扩缩容、独立凭证管理 |
| **B. 内嵌调用** | 本地开发 / 极小规模 | 平台进程内直接调用模型服务代码（或直连 provider），无需跑两个进程 |

这样"解耦"不以"运维翻倍"为代价，且**从 B 迁到 A 无需重写**。
关键：**接口契约在两种形态下完全一致**，形态只是部署选择。

### 9.1 评审意见（后端 agent · 2026-10-06）

**总评**：方向与边界铁律认同，§10 十条红线无异议；§1.1/§4.7/§5.8 的现状引用经代码
核对属实（`usage_logs` 已有 `model`/`model_upstream`/`provider` 列；平台 429 双义约定
与 quota/ratelimit 分层与已实现一致）。进入 S1 定案前建议修正/补充以下 6 项：

1. **Q3 与 §4.5 成本契约冲突**：LiteLLM Proxy 原生不返回 `x_model_service.*`，也没有
   `/v1/capabilities`。Q3 若选 C，必须写明 Proxy 阶段的交付边界——基础 chat/models
   可得，成本与能力契约**不可得**，过渡期成本回落平台价格表（现状 `needs_review` 兜底）。
2. **Q1-B 应写成优先级链而非替换**：`模型服务 cost_usd(exact) > 平台价格表 > needs_review`。
   否则 S6 切换前有成本核算空窗；"平台移除 litellm 依赖"是 S6 之后的独立决策，勿与 Q1 捆绑。
3. **②层鉴权未定义**：服务间凭证形态（静态 Bearer？env/密钥管理？mTLS？）须在正式协议
   （S2）前补一节，否则 Q 全部定完也写不出可执行的契约。
4. **Q4 依赖 Q3**：Proxy 做不到独立终止事件（B）也不发扩展字段。现实路径 = 过渡期无
   成本字段（回落价格表），自研后再按 Q4-B 投递。
5. **Q5-B 有前端迁移成本**：前端 `c794aea` 刚按"Retry-After 有无"实现 429 分流。平台
   对外契约建议**加法演进**（新增 `error.code`，旧约定标记弃用但保留一个版本），模型服务
   协议内部直接用 `code`；该变更须走 `AGENTS.md`「三」。
6. **执行缺口**：§5.6 的平台侧熔断未列入 S1–S7（建议入 S4 验收）；红线 6"取消传播"需
   S3/S4 各配一个验收测试（平台断开 → 上游真的停）；RemoteBackend 的契约测试需要一个
   fake model-service 桩，应写进 S2 的契约测试清单。

**Q1–Q9 立场**：Q1=**B**（附上述优先级链）｜Q2=**A 生产默认**（B 可选降级链，C 仅开发）｜
Q3=**C**（附边界 1）｜Q4=**依赖 Q3，自研后选 B**｜Q5=**B**（平台侧加法迁移）｜Q6=**A**｜
Q7=**B**｜Q8=**B**（合规否决权 + `compliance_denied` 码）｜Q9=**C**（平台账本为业务真源，
与 billing 已实现一致）。

> Q1/Q2/Q3 为阻塞项，最终由用户（决策人）拍板；本节意见供会商时逐条对表。

### 9.2 定案（用户拍板 · 2026-10-09 · S1 完成）

**阻塞项结论**：

| # | 定案 | 说明 |
|---|---|---|
| Q1 | **B + 优先级链** | 成本由模型服务提供 `cost_usd`；平台采信顺序：`模型服务 cost_usd(exact) > 平台价格表 > needs_review`（按 §9.1-2 写成优先级链而非替换，避免 S6 切换前的核算空窗）。"平台移除 litellm 依赖"是 S6 之后的独立决策，不与 Q1 捆绑。 |

| Q3 | **C：LiteLLM Proxy 起步 → 逐步自研** | 协议作为稳定层、实现可替换。接受 §9.1-1 的边界：Proxy 阶段拿不到 `x_model_service.*` 与 `/v1/capabilities`，过渡期成本回落平台价格表（`needs_review` 兜底）；自研后才启用 Q1-B 的 exact 成本与 Q4-B 的投递方式。 |

## 10. 附：设计红线（供评审时逐条检验）

1. 模型服务不得知道 `user_id` / `conversation_id` / `persona`。
2. `cost_usd` 未知时返回 `null`，**绝不返回 0**。
3. 平台账本必须同时可查逻辑模型名与实际 `model_used` + `provider`。
4. 模型服务无状态、可随时重启、可多副本。
5. 合规策略优先于调用方请求，调用方不可放宽。
6. 平台断开连接时，模型服务必须中止上游请求（不能继续烧 token）。
7. 协议版本不兼容时**启动即失败**，不留到运行时。
8. 超时预算分层：模型服务内部超时 < 平台总超时。
9. 平台侧 mock 后端**不得**作为生产降级路径（会假装成功）。
10. 一套代码两种形态：从内嵌迁到独立进程不需重写。
