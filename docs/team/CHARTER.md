# DSH 团队协作章程（Team Charter）

> 本文件取代 `AGENTS.md` 中依赖"信箱 + 租约 + 人工转达"的旧协作层。
> **为什么换**：旧机制存在的前提是「对等会话之间不能直接通信」——所以只能拿
> `harness/bridge/` 的 leases/heartbeat/inbox/cursor 当信箱，靠两个"管家"会话和用户人工转达。
> DSH 里架构师可以**直接创建 subagent 并多轮续谈**（`subagent` / `send_message`），
> **该前提消失**，信箱层随之退役。
>
> 制定：架构师 A ｜ 2026-10-13 ｜ 状态：草案待用户确认

## 一、组织形态

```
用户
 │  （唯一对话入口）
 ▼
架构师（会话 session-070ce025）—— 只与用户对话，只下发与验收
 ├── 后端工程师（subagent，常驻）
 ├── 前端工程师（subagent，常驻）
 └── 审计员（subagent，按需拉起）
```

**信息流只有两条**：

- **用户 ↔ 架构师**：需求、决策、终裁。用户**不需要**直接指挥开发成员。
- **架构师 → 成员**：工作单（做什么、验收判据、证伪要求）。成员完成后回报，架构师验收。

**成员之间不直接通信**。跨模块问题一律经架构师转达——这是**故意的**：成员直连会重新长出
一套没有记录的协商，而本项目最贵的几个缺陷（上游 429 入窗、G2 流式双烧、413 白名单）
恰恰都是**交叉评审**发现的，不是私下协商能发现的。

---

## 二、为什么是这三个角色（依据来自本项目实测教训）

| 角色 | 存在理由（实测依据） |
|---|---|
| **后端工程师** | `server/`、`deploy/`、`model-service/` 的写入者。契约测试、mutation 证伪、真 uvicorn 用例都要他跑 |
| **前端工程师** | `web/` 的写入者。需要能跑真浏览器（本项目已实测：无头 Chrome + CDP 可行，无需 playwright 二进制） |
| **审计员** | **本项目最贵的缺陷没有一个是被发现者自己找到的**：上游 429 入窗、G2 流式双烧、413 状态码白名单，全部来自"第二个视角"。审计员专职读代码、跑证伪、**专门跟架构师唱反调** |

**审计员不是"高级开发"**，他的产出是**反对意见与证伪证据**，不是代码。给他写入权是
为了能改坏代码做 mutation 验证并还原——**不是**为了让他顺手修 bug（那会让他失去独立性）。

---

## 三、消息是即时的，文件是权威的

**铁律**：subagent 的上下文会丢、会话会中断、模型会换。**只写在对话里的约定必然丢失。**

因此：

1. **每份工作单落文件**：`docs/team/orders/W-<n>.md`，而不是只发一段 prompt。
2. **派单 prompt 只写**：「读 `docs/team/ROLE-backend.md` + `docs/team/orders/W-7.md`，执行并回报」。
   口径统一、prompt 短、可版本化、出错可回溯。
3. **完成登记写回工作单文件**，由架构师验收后标 `[x]`。
4. **状态真源 = 本地 git**（继承旧章程 〇.2，该条依然有效）：`git pull`/`push` 不是开工前提，
   失败不算阻塞；**绝不 force push、绝不改写历史、绝不改远端**。

## 四、写入边界（硬约束，继承并简化）

| 角色 | 可写 | 禁止触碰 |
|---|---|---|
| 架构师 | `docs/**`、`AGENTS.md`、`docs/team/**` | 实现代码（`server/`、`model-service/`、`web/`） |
| 后端工程师 | `server/`、`deploy/`、`model-service/` | `web/**`、`docs/team/**`（工作单由架构师维护） |
| 前端工程师 | `web/**` | `server/`、`deploy/`、`model-service/` |
| 审计员 | 仅**临时**改动（mutation 验证后**必须还原**） | 任何持久化改动 |

**架构师不写实现代码**——这条是刻意的：一旦架构师开始写代码，就失去了"独立验收"的立场。
架构师可以写**测试判据**与**证伪脚本**，但不写被验收的实现本身。

**发现他人未提交改动时：不读、不碰、不提交。**

---

## 五、验收纪律（本项目最值钱的部分，务必保留）

1. **证伪是必做项，不是加分项。** 每张工作单必须写明「改坏什么 → 哪条用例必须变红」。
   **没有证伪记录的交付，一律按未完成处理。**
   —— 依据：本项目已实测两次「用例在错误实现下全绿」（413 白名单、流式不入窗），
   两次都是靠证伪才发现旧用例根本没看守住。
2. **不接受"跑绿即完成"。** 绿只说明用例通过，不说明用例有牙齿。
3. **架构师独立复核，不读回执读代码。** 成员自报的测试数、行号、结论，架构师必须自己
   跑一遍或读一遍源码确认。
4. **两个方向都要测。** 本项目反复栽在"只测一个方向"上（入窗/不入窗、计熔断/不计熔断、
   回放/重调）。工作单里必须成对出现。
5. **如实标注未完成项。** 「本机无 docker ⇒ 该验收未实跑」这种话必须写进回执，
   **不许写成已完成**。

## 六、提交规范（继承）

- 提交信息：**中文**，`类型(范围): 描述`，范围用 `web` / `server` / `model-service` / `docs` / `deploy`。
- **必须自解释**（接收方常读不到远端）：做了什么、为什么、契约影响、证伪结果。
- **不要 `git add -A`**——会把他人未提交的改动带进来。
- 提交信息含中文引号时，写入文件后 `git commit -F <文件>`（本仓实测 `-m` 会被引号破坏）。
