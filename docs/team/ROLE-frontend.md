## 三、浏览器验证：本机可行，别用"没有 playwright"当借口

**本项目已实测：用真实 Chrome（headless + CDP）驱动真实页面是可行的，零额外依赖。**
（前一位前端工程师用这条路跑通过：逐格读 DOM 文本与控制台，两档传输各出一份结果 JSON + 截图。）

**因此**：涉及用户可见行为的改动，**必须**做浏览器实弹，读 DOM 而不是读自己的想象。

**必须覆盖的格子**（本项目已有先例，照做）：
- **深浅两主题 × 桌面/窄屏（390px）四格**；
- **文字对比度**：本项目的质量标准是 **WCAG 4.5:1**。已有常驻夹具
  `web/scripts/contrast-audit.mjs`，新页面请一并纳入。
  ⚠️ 本项目实测过两种翻车：① 用**纯白底**算对比度，而真实卡片是**半透明白压在淡紫底上**
  （算得 4.76，真值只有 4.32）；② 把**渐变背景**当纯色算，产生测量假阳性。**算对比度必须取真实合成色。**
- **零控制台报错**——且要先注入一条 `console.error` 自证捕获有效，再声称"其余各格 0 报错"。

## 四、本项目的前端实测纪律（都是踩过的坑）

### 4.1 流式错误的三个判据（与后端契约强相关）

1. **流式路径拿不到 `Retry-After` header**（响应头在错误发生前就发完了）⇒
   退避时长**只能**从错误体的 `error.retry_after_s` 读。
2. **`[DONE]` 是唯一正常收尾信号**，无论成功还是错误。判断"流被异常截断"请看
   **连接断开 / 没有 `[DONE]`**，**不要**看"最后一个 chunk 是不是 content"。
3. **例外**：绝对上限（`stream_max_duration`）按协议**不给**错误帧，对外就是
   "回复中断 + `[DONE]`"。所以"没收到错误帧但内容不完整"是**合法状态**，别当解析失败。

### 4.2 422 的 `detail` 是数组，不是字符串

原生面 `/api/v1/*` 的 422：`detail` 是 **list**，字段名在 **`loc` 的末段**。
已实现 `Array.isArray(detail)` 分支 + `ApiError.fieldErrors`，**不要退回**"请求失败 (422)"。

⚠️ **`input` 字段带的是用户提交的原值**——实测注册弱密码会得到 `input="123"`。
**绝不要把 `input` 渲染进界面或塞进错误上报**（等于把用户刚敲的密码回显并持久化）。

### 4.3 兼容面 `/v1` 的 422 不可解析

它的 `message` 是 Python 字面量（单引号），**不是 JSON**。`web/` 全部调用走 `/api/v1`，
没有 `/v1` 消费方 ⇒ **别为它写解析分支**。

### 4.4 不要重发会重复落库的请求

已核实：失败时前端会**重拉服务端消息**，而阶段A已把用户消息落库 ⇒
**纯前端重发会造成用户消息重复落库**。要重试必须先确认该路径不会重复写。

## 五、环境与命令

```powershell
cd D:\workingcode\chatbot-platform\web
npm test          # 前端用例
npm run typecheck
npm run lint
```

**已知坑**：
- **同项目并跑两个 `next dev` 会共用 `.next`** —— 带 `NEXT_PUBLIC_API_BASE` 的那台会把
  地址烤进编译产物、把另一台带坏。**单台串行，切换前清 `.next`。**
- **端口要避开后端假模型服务的控制面**（`/__control/scenario`、`/health/liveness`、
  `/v1/chat/completions`）——已有一次撞端口吃到 404 的记录。
