## 1. 背景：为什么要做

`MS_UPSTREAM_FIRST_CONTENT_TIMEOUT` 与流式心跳在 RB-1/RB-2 已落地（`dd0bd78`），
但平台的**启动自检**还不知道这两件事：

- 平台红线 8 断言按**流式空闲上限**（`model_service_stream_idle_timeout`）对标所有内层超时；
- 而一旦模型服务会发心跳，平台对流式的真实保护上限是**绝对上限 180s**——
  此时一个合规的 120s 内层预算会被**误判为违规**，启动被拒。

⚠️ **一处纠正（v1 写错）**：v1 说"用的是写死的 90s"——**不准确**。
`server/app/llm/model_service_ops.py:120` 读的是 `s.model_service_stream_idle_timeout`，
**90.0 只是它的默认值**（`server/app/config.py:49`）。
⇒ 实施姿势**不是"把常量 90 换成 180"，而是"在两个配置源之间按 keepalive 选一个"**。

⚠️ **另一处已发生的失效必须避免重演**：P2-2 当年**名义闭合、实则空转**。真相有**两个叠加成因**：
1. `model_service_ops.py:129-130` 的 `if inner is None: continue` —— 缺键逐条跳过，不报错；
2. `:119` 末尾的 `or {}` —— 整个 `timeouts` 块缺失时每个键都是 `None`、**全部 `continue`**，
   断言**一条都不执行、零日志零警告**。

**本单判据 A3 的 mutation 就是冲着它去的。**

## 2. 做什么

### RB-3-1 `features.timeouts` 新增 `upstream_first_content_s`

**实测落点**：端点 `model-service/msvc/main.py:526`；`features` 起于 `:531`；
**`timeouts` 块 = `:538-542`**（§8.1-2 注释在 `:537`）。

```python
                # §8.1-2：暴露实际超时值供平台启动断言「内层 < 外层」
                "timeouts": {
                    "upstream_first_token_s": s.upstream_first_token_timeout,
                    "upstream_first_content_s": s.upstream_first_content_timeout,   # ← 新增（:539/:540 之间）
                    "upstream_chunk_idle_s": s.upstream_chunk_idle_timeout,
                    "upstream_total_s": s.upstream_total_timeout,
                },
```
字段确认：`upstream_first_content_timeout`，`model-service/msvc/config.py:51`，`float = 60.0`。
顺序依据：协议 §8.1 硬约束 2 的示例顺序为 `first_token → first_content → chunk_idle → total`。

### RB-3-2 `features.stream_keepalive` —— **必须推导，绝不写死**

**裁定：`"stream_keepalive": s.upstream == "litellm"`**

**为什么不能写死 `true`**（侦察实测证据链）：

| # | 事实 | 位置 |
|---|---|---|
| 1 | 代码里**没有任何 keepalive 配置开关**（21 个字段无一相关） | `model-service/msvc/config.py:16-76` |
| 2 | 心跳唯一来源是 event 流；`{"kind":"keepalive"}` 由**上游形态**决定 | `main.py:404-406` |
| 3 | 真实上游：任何「无 `delta.content` 且无 `finish_reason`」的 chunk ⇒ 心跳 | `provider.py:326-336` |
| 4 | 假上游：受 `Scenario` 控制，**默认 `reasoning_only_chunks=0` ⇒ 一行心跳都不发** | `provider.py:145-147`/`:172-173`/`:49-53` |
| 5 | 生产 app 用 `Scenario()`（默认） | `main.py:589` |
| 6 | **默认部署就是假上游** | `deploy/docker-compose.yml:66`、`deploy/.env.example:36` |

⇒ **写死 `true` 在出厂默认配置下是假声明**：平台据此对标 180s，而服务一行心跳都不发 ⇒
运行期 90s 空闲上限照旧先触发、把归因抢走。**这正是"虚假的安全感"，且默认部署下 100% 复现。**

**放置位置**：`features` 层，建议 `:536` 之后、`timeouts` 之前（与 `idempotency_window_seconds` 同层，
都是"服务自述特性"）。**它是布尔特性位、不是超时 ⇒ 不能塞进 §3 的超时循环。**

### RB-3-3 平台自检：`upstream_first_content_s` 进循环，`stream_keepalive` 独立检查

**实测落点**：`server/app/llm/model_service_ops.py:110-137`。

- `upstream_first_content_s` 加入 `:121-127` 的**超时键元组**；
- `stream_keepalive` 是布尔位 ⇒ **独立一次存在性检查**（不走超时循环）；
- **删掉 `:129-130` 的 `continue`**，改为抛 `ProtocolVersionError`（缺键即失败）。

⚠️ **顺手改掉那句假注释**（`model_service_ops.py:130`）：
```python
            continue  # Proxy 过渡期无 capabilities 契约 → 跳过（§8.3）
```
**它的理由是假的**：proxy 模式在 `:88-100` **已提前 `return`**，根本走不到这个循环。
它保护的不是 proxy，只是把 native 路径的缺键静默吞掉。**必须连同注释一起改成真实理由**
（否则后人还会照它"缩范围"——角色卡 §3.4 明令禁止该模式）。

### RB-4 红线 8 断言：按 keepalive 分档

**实测落点**：判定在 `model_service_ops.py:131-136`。

- **180s 请复用现成常量** `model_service_stream_max_duration`（`server/app/config.py:53`，`180.0`），
  **不要新造**；
- `keepalive=true` ⇒ 外层取 **180s**（绝对上限）；`false` 或**缺失** ⇒ 取
  `model_service_stream_idle_timeout`（**保守侧**，默认 90s）；
- **报错文案必须参数化**（现硬写"平台流式空闲上限"+ 建议调 `MODEL_SERVICE_STREAM_IDLE_TIMEOUT`）
  —— B2 判据明写「按保守侧给出**原因**」，文案不改就满足不了。

#### ⚠️ 硬护栏：`upstream_total_s` **不得**纳入 keepalive 开关

协议明写 `upstream_total_s` **仅约束非流式**、按"平台读超时口径"对标
`model_service_timeout_total`（`config.py:43`，`120.0`）。
现行代码把它跟流式键一起比 90s（靠 `60 < 90` **侥幸通过**）——这是**已存在的第三处缺陷**。

**本次裁定**：**不动它的对标基准**（保持现状 ⇒ 更保守、方向安全、且不打红既有用例），
但**绝对不许**把 keepalive 开关套到整个循环——否则 `keepalive=true` 时它会被放宽到 180，
**把一条非流式预算放过了头**。该缺陷**另立工作单**（见 §9）。

### ⚠️ A3 的用例必须有牙齿

mutation **能打红**（"跳过"版当下就在 `:129-130`，`git blame` 显示来自 `a6394465`），但用例**必须构造正确**：

- 必须构造**「其余键全合法、只少这一个键」**的 capabilities，断言 `pytest.raises(ProtocolVersionError)`；
  **若给一个整体崩溃的 payload**（例如 `protocol_version` 错），失败会发生在 `:104-108` 的版本检查上，
  **`continue` 与否都红 ⇒ 用例无牙齿**（正是角色卡 §二警告的"绿灯不等于有牙齿"）。
- 断言**缺失的键名出现在报错里**；**不要**只断言 `"红线 8" in msg`（太弱、无法定位）。
- **两条路径各一条用例**（走循环 / 走独立检查），否则其中一条分支无人看守。

### ⚠️ B2 单独不够，必须与 B1 配对
