## 1. 需求拆成两项（互相独立，都要做）

### 1-1 「思考中」状态 ＋ 异常必须及时反馈

**现状**：`send()`（`page.tsx:229`）在请求发出后立刻插入一条空的 assistant 气泡
（`:239-241`），**在收到首块前它是完全空白的**。MiMo 要 12 秒才吐首字 ⇒ 用户看到 12 秒空白，
**无法区分"在思考"和"卡死了"**。

**要做**：
- 发出请求后，assistant 气泡内显示**思考中指示**（文案如「思考中…」，配轻量动画）；
- **首块内容到达 ⇒ 立刻撤掉指示**（不能与内容并存）；
- ⚠️ **异常必须立刻反馈**——这是用户明确点名的：
  - 收到**流内错误帧**（`api.ts` 会抛错）⇒ 撤掉"思考中"，把错误显示出来；
  - 开流前就失败（如 502 `LLM upstream error`）⇒ 同样立刻显示错误；
  - **绝不允许"思考中"在错误发生后继续转**——那会让用户以为还在重试。
- **超时兜底**：若长时间无任何块且无错误（例如 >45s），显示可区分的提示
  （如「仍在等待模型…」），**不要**直接报错（长推理是合法的）。
  那个 45s 必须是**常量 + 注释说明依据**（本单实测首块 12s，取 ~3.7× 余量）。

### 1-2 自适应节奏缓冲（**核心**，用户的「丝滑」「不能设阈值」）

**目标行为**：
- 上游**吐字慢** ⇒ 按**真实速度**显示（不额外加延迟）；
- 上游**吐字极快**（如 0.6s 吐完）⇒ **压速**，像真人打字；
- 上游**完全不吐**（思考中）⇒ 由 1-1 的指示兜着。

**❗ 硬约束：不得用阈值/分档（用户明确否决）**

不许写这类代码：
```ts
if (queue.length > 200) speed = 5;      // ❌ 分档
else if (queue.length > 50) speed = 20; // ❌ 阈值
```

**要写成连续函数**（建议形式，实现者可微调参数但要保持"连续、无分支"）：

```
释放速率(字/秒) = BASE × e^(q / K)
    q = 已到达但尚未显示的字符数（积压）
    BASE = 30   （q→0 时的速率 ≈ 真人打字；此时等于真实速度）
    K    = 360  （积压 360 字 ⇒ 速率 ×e ≈ 2.7×；积压 1000 字 ⇒ ×16）
```

**为什么这样满足用户的两条要求**：
1. **慢则真实**：上游慢 ⇒ `q` 始终很小 ⇒ `e^(q/K) ≈ 1` ⇒ 速率 ≈ BASE
   且**实际显示速度由上游到货节奏决定**（队列常常是空的）。
2. **快则压速**：上游爆发 ⇒ `q` 一次性变大 ⇒ 速率连续抬升，**平滑追赶，无跳变**。
3. **"按字符数量来定"**：速率**唯一自变量就是积压字符数** `q`，没有别的判据。
4. **有上界**：2000 字积压时速率 ≈ 30×e^5.6 ≈ 8000 字/秒 ⇒ 秒级追平，
   **不会让用户等几分钟**（这是"丝滑"的必要条件——只慢不快会变成新问题）。

**实现要求**：
- 用**单个 `requestAnimationFrame`/定时器循环**驱动释放，**不要**每个 delta 各起一个定时器；
- 组件卸载、切换会话、`stopStreaming()` 时必须**清理循环**（否则内存泄漏 + 幽灵更新）；
- **点「停止」** ⇒ 立刻停止缓冲并**把已到内容一次性显示**（不能丢已生成的内容，
  也不能继续慢慢放）；
- **落库不受影响**：显示层缓冲，服务端照常立刻存完。`send()` 末尾
  `setMessages(await platformApi.messages(...))`（`:260`）会用服务端版本覆盖显示
  ⇒ **务必确认这一步不会把"还没放完的缓冲"跳成完整内容而造成视觉跳变**：
  正确做法是**等缓冲排空后再 refetch**（或 refetch 后立即用最终文本替换且不打断动画）。
  ⚠️ **这一条最容易做错，请实测**（见 §3 判据 R3）。
- **`prefers-reduced-motion`**：该偏好为真时**关闭缓冲**（直接实时显示），
  这是无障碍要求，也是"用户明确不想要动画"时的正解。

## 3. 验收判据（每条要能红）

| # | 判据 | 怎么打红（mutation） |
|---|---|---|
| **C1** | 请求发出 ⇒ 气泡内出现「思考中」；首块到达 ⇒ **指示消失且不残留** | 去掉首块时清除指示 ⇒ 红（指示与内容并存） |
| **C2** | **流内错误帧**（如 `rate_limited`）到达 ⇒ 指示立刻消失、错误显示 | 让错误路径不清指示 ⇒ 红（指示继续转） |
| **C3** | **开流前失败**（HTTP 502 `LLM upstream error`）⇒ 指示消失、错误显示 | 同上 ⇒ 红 |
| **S1** | **上游快**（构造 0.2s 内到达 300 字）⇒ 显示**明显慢于**真实到达（用时 > 2s），且**无跳变** | 去掉缓冲 ⇒ 红（0.2s 内全部显示） |
| **S2** | **上游慢**（构造每 100ms 一个字）⇒ 显示**基本实时**（总显示时长与真实时长差 < 1s） | 把速率写死成小常数 ⇒ 红（越积越多、越拖越久） |
| **S3** | **速率无阈值分支**：`q` 连续变化时速率连续变化（代码审查 + 若可能，单测解析式） | 引入 `if (q > N)` 分档 ⇒ 红（人工核对即可） |
| **R1** | `stopStreaming()` ⇒ 循环停止、已到内容**一次性显示齐全** | 停止时不排空 ⇒ 红（内容丢失） |
| **R2** | 切换会话 / 卸载组件 ⇒ **无定时器泄漏**（无 `setState on unmounted` 警告） | 不清循环 ⇒ 红 |
| **R3** | **流结束后 refetch 不产生视觉跳变**（缓冲未放完时 refetch 不得把文本瞬间补全） | 提前 refetch ⇒ 红（肉眼看得到跳变） |
| **R4** | `prefers-reduced-motion: reduce` ⇒ 缓冲关闭、实时显示 | 忽略该偏好 ⇒ 红 |

**C1–C3 是用户点名要的**（"模型异常时及时反馈"），**S1/S2 是"丝滑"的正负两面**，
**R3 是最容易漏的**。
